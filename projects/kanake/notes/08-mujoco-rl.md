!!! summary "한눈에 보기"
    - **목표:** 실제 뱀이나 새처럼 **머리 시선은 고정**하고, 몸은 **S자(serpentine)**를 그리며 속도 명령을 따라가게 한다. 잘 되면 머리 방향 명령을 따로 줘서, 머리를 돌려도 몸은 속도를 따라가게 한다.
    - **왜 Isaac에서는 사이드와인딩만 나왔나:** 마찰이 **등방성**이었기 때문이다. serpentine은 몸 옆방향 마찰이 길이방향보다 커야 앞으로 간다. 같은 serpenoid 보행을 등방성 마찰 0.7에서 돌리면 **오히려 뒤로 간다(−0.02 m/s)**. MuJoCo에서 링크를 캡슐로 바꾸고 **축 0.2 / 옆 1.0** 이방성 마찰을 주자 +0.16 m/s로 전진했다.
    - **평지 결과(v4):** 0.05–0.15 m/s 명령을 오차 0.014 m/s 이하로 따라가고, 머리 yaw 오차는 1° 안팎이다. 머리 방향 명령 ±30–40°에서도 속도를 그대로 유지했다.
    - **실패:** 머리를 5–10 cm 들고 가는 자세(v5, v6)는 목 자세 사전과 게인 상향(kp 10)까지 넣었지만, 정책이 목을 비튼 채 제자리에서 버티는 쪽으로 수렴해 포기했다.
    - **지형(v7, v8):** Teraffe와 같은 7종 지형과 같은 최종 난이도(높이 12–30 cm, 계단 6–12 cm, 턱 10–20 cm)로 5단계 커리큘럼을 학습했다. 막히는 원인(작은 pitch 범위, 중력 기준 머리 수평 보상, 마찰 한계)을 하나씩 고친 v8은 **3 cm 계단을 30초에 2–3단** 오르지만, **6 cm는 첫 단에서 막힌다**. Teraffe 최종 난이도의 계단은 아직 못 넘는다.
    - **뒤집힘 회복(v8):** 굴린 상태 시작과 외력 밀기로 학습해, **180° 완전히 뒤집혀도 2초 안에** 스스로 굴러 바로 선다.
    - **도구:** 키보드/조이스틱 조종, Teraffe식 제어판 UI(정책·지형·레벨·마찰 변경), 시나리오 평가 스크립트. 코드는 [Kanake_MuJoCo](https://github.com/seosangryeong/Kanake_MuJoCo)에 있다.

![평지 serpentine](assets/mujoco-serpentine.jpg)
*v4, 0.10 m/s 명령. 같은 고정 카메라로 4, 9, 14초에 찍은 장면. 오른쪽 끝이 머리다. 머리 쪽은 곧게 앞을 보고, S자는 꼬리 쪽으로 흘러간다.*

## 물리 모델: 충돌 형상과 마찰

### 캡슐 충돌

링크 단면이 원형이라(링크 반지름 18 mm, 커버 19 mm) CAD 메쉬의 볼록 껍질 대신 **링크마다 캡슐 하나**를 커버 외경에 맞춰 붙였다. CAD 메쉬는 보이기만 한다. 같은 등방성 조건에서 메쉬와 캡슐의 보행 결과가 같아서(둘 다 −0.02 m/s) 근사 오차는 무시할 수 있다.

### 이방성 마찰이 serpentine의 조건이다

serpentine은 휘어진 몸이 옆으로는 버티고 길이방향으로는 미끄러지면서, 옆방향 반력의 앞쪽 성분으로 나아간다. 실제 뱀은 배 비늘, 뱀 로봇은 보통 수동 바퀴로 이 차이를 만든다. 스크립트 serpenoid 보행(진폭 45°, 0.7 Hz, 한 파장)으로 마찰을 바꿔 봤다.

| 마찰 (축 / 옆) | kp 3 | kp 10 |
|---|---|---|
| 0.7 / 0.7 CAD 메쉬 (원래 설정) | **−0.023 m/s** | – |
| 0.7 / 0.7 캡슐 | −0.020 | – |
| 0.3 / 0.6 | 0.034 | 0.092 |
| 0.3 / 1.0 | 0.079 | 0.154 |
| **0.2 / 1.0** (v2–v7 기본) | 0.164 | 0.201 |
| 0.1 / 1.0 | 0.288 | 0.241 |

!!! issue "Isaac Lab에서 serpentine이 안 나온 이유"
    **문제:** Isaac Lab에서 아무리 학습해도 사이드와인딩으로만 갔다.
    **원인:** 물리 엔진이 아니라 마찰 모델이었다. Isaac Lab의 재질은 정지·동마찰 계수 하나씩인 등방성 모델이고, 등방성 마찰에서 serpentine은 추진력이 없다. 사이드와인딩은 몸을 들어 접촉점을 바꾸므로 등방성에서도 간다. MuJoCo에서도 원래 설정(등방성 0.7)에서는 똑같이 사이드와인딩이 나왔다.
    **해결:** MuJoCo는 캡슐–평면 접촉의 첫 접선을 캡슐 축에 맞춘다. 접촉 쌍(`<pair friction="축 옆 …">`)으로 축과 옆 마찰을 따로 줬다.

!!! lesson "실물에 주는 의미"
    실제 커버가 등방성이면 실물도 serpentine으로 앞으로 가지 못한다. 시뮬레이션은 축 0.2 / 옆 1.0(나중에 1.5)을 **가정**한 것이다. 실물에 옮기려면 비늘 모양 돌기, 한 방향으로 누운 섬유, 얇은 리브 같은 방향성 커버나 수동 바퀴가 필요하다. 커버의 길이·옆 방향 마찰을 재서 넣는 것이 다음 할 일이다.

### 평면 밖에서는 접촉 쌍이 동작하지 않는다

| 접촉 대상 | 첫 접선과 캡슐 축의 정렬 |
|---|---|
| 평면 | 항상 정렬 |
| 박스, 메쉬, heightfield | 월드에 고정 (캡슐 방향과 무관) |

지형에서는 접촉 쌍이 "링크 옆"이 아니라 "월드 y방향"에 마찰을 준다. 그래서 지형용으로 **외력 방식**을 만들었다. 접촉은 축 마찰로만 풀고, 매 물리 스텝(400 Hz)마다 접촉점에서 링크 축에 수직인 미끄러짐 속도를 구해 `(μ옆 − μ축) × 수직항력`만큼 반대 방향 힘을 더한다.

!!! issue "외력 방식 마찰이 첫 스텝에 발산"
    **문제:** 특정 시드에서 로봇이 첫 스텝에 (139, −130, −56) m로 날아갔다.
    **원인:** 힘을 명시적으로 적분하는데, 미끄러짐이 작을 때 실효 감쇠가 링크 질량에 비해 커서(c·dt/m ≈ 2, 안정 한계) 초기 접촉 충격에서 불안정해졌다.
    **해결:** 추가 마찰력이 한 스텝 안에 미끄러짐 속도를 뒤집지 못하도록 `|F| ≤ 0.6·m·|v|/dt`로 제한했다. 평지에서 v4를 돌리면 접촉 쌍 방식과 속도 0.095 대 0.100 m/s로 거의 같고, 계산은 약 1.7배 느리다.

## 액션: serpenoid 진행파 + 관절별 보정

관절 각도를 직접 내지 않는다. 8개 yaw 관절에 머리 → 꼬리로 흐르는 진행파를 만들고, 모든 관절에 보정값을 더한다.

```
yaw 관절 k (머리 → 꼬리):  θ_k = A · sin(φ − k·π/4) + γ + r_k     φ ← φ + 2π f Δt
pitch 관절:               θ   = r
```

| 액션 | 범위 | 비고 |
|---|---|---|
| 진폭 A | 0–60° | 0이면 몸이 펴져 정지 |
| 주파수 f | 0.3–1.2 Hz | 위상을 적분해서 주파수가 바뀌어도 파형이 이어짐. **끌 수 없음** |
| 조향 γ | ±29° | 모든 yaw 관절에 같은 오프셋 → 몸이 휘어 회전 |
| 보정 r (16개) | 머리 j1 ±1.0, 목 j2 ±1.2, 몸통 ±0.15 rad | 몸통은 80 ms 저역통과 필터 |

파형 파라미터는 0.2 s, 보정값은 80 ms 저역통과 필터를 거친다. 정책 40 Hz, 물리 400 Hz, PD는 Isaac Lab과 같은 kp 3, kv 1.

!!! issue "v1: 파형을 끄고 진동으로 미끄러지는 편법"
    **문제:** v1 정책은 주파수를 0.03 Hz로 낮춰 파형을 끄고, 몸을 굽힌 채 보정값으로 고주파 진동을 만들어 이방성 마찰 위를 미끄러졌다. 속도는 맞췄지만 serpentine이 아니다.
    **해결:** 주파수 하한 0.3 Hz(정지는 진폭 0으로), 보정값에 80 ms 저역통과 필터, 몸통 보정 범위 0.3 → 0.15 rad, 보정 크기 벌점 20배, 초기 탐색 노이즈 1.0 → 0.5. v2부터 추진은 파형이 맡고, 정책은 속도·방향 조절과 머리 안정화를 배웠다.

**왜 관절별 진폭이 아닌가.** Isaac Lab 정책은 관절 16개의 진폭을 따로 냈다. serpentine의 표준 형태(serpenoid 곡선)는 yaw 관절에 같은 진폭과 일정한 위상차를 주는 것이고, 손잡이를 3개로 줄이니 학습이 빠르고 편법도 막혔다. 대신 "앞은 들고 뒤만 S자" 같은 진폭 분포는 만들 수 없다. 계단 전략에 이 유연성이 필요해서 v9에서는 파형 관절마다 진폭을 액션으로 다시 받는다.

## 명령, 관측, 보상

- **명령:** 월드 속도 벡터(0–0.15 m/s, 방향은 몸 방향 ±1 rad, 10%는 정지)와 진행 방향 기준 머리 yaw 오프셋(±40°, 2–5초마다 바뀜). 6–10초마다 다시 뽑는다.
- **관측:** 모든 방향 값을 **명령 진행 방향 기준**으로 바꿔 넣는다. 명령, 머리 yaw 오차·각속도·자세, 몸 방향 오차, 몸 무게중심 속도(0.4 s 필터 / 순간), 꼬리 자세, 관절 위치·속도·토크, 파형 위상·파라미터, 필터된 보정값, 이전 액션.
- **속도:** 뱀은 매 순간 좌우로 흔들려서 몸 무게중심 속도를 0.4 s로 필터한 값을 명령과 비교한다.

| 보상 | 내용 |
|---|---|
| 속도 추종 | `2.0 · exp(−(‖v − v_cmd‖ / 0.04)²)` |
| 머리 yaw | 좁은 커널(9°)과 넓은 커널(29°) |
| 머리 흔들림 | 머리 3축 각속도 보상·벌점, 진행 방향 옆으로 흔들리는 속도 벌점 |
| 머리 수평 | 머리 기울기 9° 커널 (지형 climb 버전은 지면 기울기 기준) |
| 몸 방향 | 몸 평균 방향이 진행 방향을 향하도록 |
| 측면 미끄러짐 | 링크 축에 수직인 미끄러짐 속도 벌점 (사이드와인딩 억제) |
| 정규화 | pitch 각도, 몸통 보정 크기, 액션 변화, 전력 |

## 평지 결과: 시선 고정과 머리 명령

v4는 j2를 파형에서 빼서 목 관절로 바꾸고, 머리 3축 각속도에 보상을 준 버전이다. 15초 시나리오의 뒤 10초 평균.

| 시나리오 | 속도 오차 | 머리 yaw 오차 v3 → v4 | 머리 3축 각속도 v3 → v4 | 머리 기울기 v4 |
|---|---|---|---|---|
| 0.05 m/s 직진 | 0.008 | 1.5° → 0.8° | 22 → 13°/s | 1.0° |
| 0.10 m/s 직진 | 0.010 | 0.8° → 0.8° | 24 → 16°/s | 1.1° |
| 0.15 m/s 직진 | 0.014 | 1.0° → 0.7° | 30 → 22°/s | 1.6° |
| 0.10 + 머리 +30° | 0.010 | 0.5° → 0.8° | 21 → 17°/s | 2.1° |
| 0.05 + 머리 +40° | 0.012 | 1.2° → 0.7° | 23 → 15°/s | 2.4° |

머리 방향 명령이 없던 v2에 같은 머리 명령을 주면 yaw 오차가 11–34°였고, 속도도 0.015 m/s까지 무너졌다. 넘어짐은 어느 버전에서도 없었다. 액션 0(파형만)일 때는 머리 yaw 오차 13°, 각속도 65°/s였다.

![머리와 몸 무게중심 궤적](assets/mujoco-head-path.png)
*v4, 0.10 m/s. 머리의 방향(yaw)은 1° 안으로 고정되지만, 머리 위치는 몸 무게중심보다 좌우로 약 ±1.5 cm 더 흔들리며 간다.*

!!! issue "v3: 머리가 끄덕이고 기울어짐"
    **문제:** v3는 yaw 시선은 잘 잡았지만 머리 각속도를 나눠 보면 yaw 9.6°/s, **pitch 19.6°/s, roll 16.2°/s**였고, 머리를 13° 들고 다녔다. j2 명령이 −49°~+63°까지 쓰여 관절 한계(85°)에 여유도 없었다.
    **원인:** j2가 파형에 포함돼 있어서, 정책이 j2 보정값으로 파형을 거꾸로 지우면서 링크1의 흔들림까지 상쇄해야 했다. 보정값의 80 ms 필터가 위상 지연을 만들었다.
    **해결(v4):** j2를 파형에서 빼서 정책이 전담하게 하고(±1.2 rad), 머리 쪽 관절만 필터를 30 ms로 줄였다. 머리 3축 각속도 보상을 2배로, 머리 수평은 기울기 각도 커널로 바꿨다.

## 머리 들기 시도 (실패)

머리를 5–10 cm 들고 땅에 닿지 않게 하면서 시선을 고정하고, pitch도 명령으로 바꾸려 했다.

- **정적으로는 가능하다.** pitch 관절 각도를 1500개 무작위로 시험하니 머리 8 cm, 수평 ±6°, 흔들림 0.3 mm 이하의 자세가 있었다. 필요한 토크는 0.5 N·m 이하(한계 10 N·m).
- **몸 중간만 꺾으면 안 된다.** 양 끝이 바닥에 닿은 Λ자 아치가 되거나, 앞부분이 앞으로 고꾸라진다. 앞부분 무게중심이 지지 기반 위에 있어야 한다.
- **머리를 들면 느려진다.** 바닥을 미는 몸이 절반으로 줄어, kp 3에서 최고 0.035 m/s (머리 내리면 0.08 m/s). kp 10이면 0.064 m/s, 기본 자세 최적화 후 0.07–0.11 m/s.

| 버전 | 구조 | 결과 |
|---|---|---|
| v5 | 목 j1–j7 직접 제어, 높이·pitch·roll 보상 | 머리 높이 6.9 cm는 맞추지만 pitch 오차 47°, roll 64°, 파형 꺼짐 |
| v6 | 높이별 목 자세(CEM으로 찾음) + 보정, kp 10 | 모든 시나리오에서 **속도 0**. 진폭 0, roll 73°로 누운 채 버팀 |

![머리 들기 실패](assets/mujoco-lift-fail.jpg)
*v6, 0.05 m/s + 머리 8 cm 명령. 목을 비틀어 머리 높이만 맞추고 10초 동안 제자리.*

!!! lesson "배운 점"
    높이 보상은 쉽게 얻고 속도 보상은 어려우면, 정책은 높이만 맞추고 서 있는다. 머리 들기로 추진력이 절반으로 줄어드는 구조에서는 보상 균형을 맞추기 어려웠다. 그래서 머리 들기는 접고, 바닥에서 시선을 고정하는 v4를 지형으로 넓히는 쪽으로 방향을 바꿨다.

## 지형 커리큘럼

### 지형

Teraffe `procedural_terrain.py`와 같은 7종 heightfield를 쓰고, **최종 난이도도 Teraffe와 같게** 뒀다. 실제 지형은 뱀 크기에 맞춰 작아지지 않기 때문이다. 영역만 8 m × 8 m로 줄였다.

| 지형 | 최종 단계 | 0단계 (×0.15) |
|---|---|---|
| 물결 / 요철 / 둔덕 / 경사 | 높이 12–30 cm, 파장 1.2–2.8 m | 1.8–4.5 cm |
| 계단 | 단 6–12 cm, 최대 누적 36 cm | 0.9–1.8 cm |
| 턱 | 10–20 cm | 1.5–3 cm |

![최종 단계 지형 예시](assets/mujoco-terrain-bank.png)
*최종 단계(높이 ×1.0) 지형 은행의 예시. 중앙 4 m × 4 m, 어두울수록 높다.*

| 단계 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 높이 배율 | ×0.15 | ×0.30 | ×0.50 | ×0.75 | ×1.0 |
| 평지 비율 | 80% | 60% | 35% | 15% | 5% |

환경마다 따로 승급·강등한다. 에피소드 평균 속도 오차가 0.035 m/s 미만이고 넘어지지 않으면 한 단계 올리고, 0.07 m/s 초과이거나 넘어지면 내린다.

### 막힌 원인과 고친 것

!!! issue "경사: 축 마찰을 올리면 더 못 오른다"
    **문제:** 물결과 경사에서 잘 못 갔다. 처음에는 축방향 마찰 0.2가 너무 미끄러워서라고 봤다(몸이 오르막을 향하면 tan⁻¹ 0.2 ≈ 11°부터 미끄러짐).
    **확인:** 중력을 기울여 균일한 오르막을 만들고 v7을 0.08 m/s로 돌렸다.

    | 축 마찰 (옆 1.0) | 0° | 10° | 15° | 20° | 25° |
    |---|---|---|---|---|---|
    | 0.2 | +0.087 | +0.053 | +0.024 | −0.010 | −0.446 |
    | 0.35 | +0.067 | +0.028 | +0.001 | −0.033 | −0.094 |
    | 0.5 | +0.044 | +0.005 | −0.016 | −0.042 | −0.074 |

    축 마찰을 올리면 옆/축 비율이 줄어 추진력이 줄고, 오히려 더 못 오른다. 순수 serpentine의 오르막 한계는 약 15–18°이고, 물결은 2단계(최대 약 21°)부터 이보다 가파르다.
    **해결:** UI에서 옆 마찰을 바꿔 보니 **축 0.2 / 옆 1.5**에서 지형을 잘 넘었다. v8부터 옆 1.5로 학습한다. 남은 원인은 몸을 들어 걸치는 pitch 동작이다.

!!! issue "둔덕: 머리가 박히고 중간 링크가 뜬다"
    **문제:** v7은 둔덕을 오를 때 머리가 경사면에 박히고, 몸 중간 링크가 공중에 떠서 바닥을 밀지 못했다.
    **원인:** 몸통 pitch 보정이 ±9°라 몸이 둔덕을 따라 휘지 못했다. 그리고 머리 수평 보상이 **중력 기준**이라 오르막에서도 머리를 수평으로 유지하려다 코끝이 박혔다.
    **해결(v8):** 몸통 pitch 범위를 ±1.2 rad(69°)로 넓히고, 머리 수평 기준을 **머리 아래 지면 기울기**로 바꿨다(머리 앞뒤 5 cm 지면 높이로 기울기 계산). 지면에서 1 cm 넘게 뜬 링크 비율에 벌점을 줬다. 지형 정보는 보상 계산에만 쓰고, 정책은 지형을 보지 않는다.

### 계단과 턱을 위한 v8 구조

뱀은 단의 수직면(라이저)에 기대 몸을 올리고, 모서리에 걸친 뒤 기대는 링크를 늘려 간다. 지형을 미리 보지 못해도 닿은 순간 관절 토크와 위치 오차로 알 수 있다.

| 항목 | 대상 | 내용 |
|---|---|---|
| 몸통 pitch 확장 | 정책 | 보정 범위 ±0.15 → ±1.2 rad |
| 고유감각 이력 | 정책 | 최근 0.5 s(2스텝 간격 × 10) 관절 위치 오차, 토크, 머리·꼬리 자세 (프레임당 38, 총 380) |
| 지형 높이 | critic만 | 몸 중심 기준 진행 방향 −0.4–+0.6 m × 좌우 ±0.2 m, 55점 |
| 물리 정보 | critic만 | 마찰, 지형 단계, 몸 바로 섬 정도 |
| warm start | – | v7 가중치를 복사하고 새 입력은 0, pitch 출력은 범위가 넓어진 만큼 줄여 처음에는 v7과 똑같이 움직임 |

### 계단을 실제로 넘었나

지형 은행 위에서 이동 거리로 속도를 재면, 단을 따라 옆으로 간 것도 속도로 잡혀 과대평가된다. 그래서 단이 +x 방향으로 5개 있고 디딤판이 35 cm인 계단 앞에 세우고, +x로 0.08 m/s 명령을 30초 준 뒤 **몸 중심 아래가 몇 번째 단인지**를 셌다 (시드 3개).

| 단 높이 | v7 | v8 (최종) |
|---|---|---|
| 3 cm | 0, 0, 0단 (첫 라이저 앞에서 막힘) | **3, 3, 2단** |
| 6 cm | 0, 0, 0단 | **1, 1, 1단** (첫 단 위에서 막힘) |
| 9 cm | 0, 0, 0단 | 0, 0, 0단 |

![계단 오르기](assets/mujoco-stairs.jpg)
*v8, 단 3 cm 계단. 옆에서 본 고정 카메라로 5, 15, 30초. 30초에 3단째에 있다.*

v8은 v7이 전혀 못 넘던 계단을 넘기 시작했지만, 아직 **로봇 두께(3.8 cm) 정도의 단**까지다. Teraffe 최종 난이도의 6–12 cm 계단은 첫 단에서 막힌다. 학습 중 평균 지형 단계는 3.89/4까지 올랐는데, 이는 계단·턱을 비스듬히 피해 가도 속도 오차 기준을 통과할 수 있어서다. 승급 기준이 "단을 실제로 넘었는가"를 보지 않는 것이 한계다.

| 최종 학습 지표 (v8) | 값 |
|---|---|
| 평균 지형 단계 | 3.89 / 4 |
| 속도 (명령 / 실제) | 0.083 / 0.072 m/s |
| 뜬 링크 비율 | 7.6% (1150회 때 15%) |
| 머리 기울기 오차 (지면 기준) | 5.0° (1150회 때 11.5°) |

평지 성능은 유지됐다. 0.05–0.15 m/s 직진, 90° 회전, 머리 ±30–40° 명령에서 속도 오차 0.010–0.014 m/s, 머리 yaw 오차 0.4–1.3°, 넘어짐 0회. 머리 3축 각속도는 17–21°/s로 v4(13–22°/s)와 비슷하다.

## 도메인 랜덤화와 뒤집힘 회복

| 항목 | 범위 |
|---|---|
| 링크 질량 | ±10% |
| 마찰 | 축 ×0.7–1.4, 옆 ×0.8–1.2 (에피소드마다) |
| kp / kv | ±10% |
| 뒤집힌 상태 시작 | 에피소드의 25%, 길이축 기준 ±180° |
| 외력 밀기 | 평균 8 s마다 옆방향 속도와 길이축 회전 충격 |
| 관측 노이즈 | 0.01 (critic은 노이즈 없음) |

뒤집혀서 yaw 관절이 수직으로 서면 S자 파형이 바닥을 밀지 못한다. 링크마다 "위쪽" 축이 하늘을 향하는 정도로 바로 섬 보상을 줬다.

평지에서 몸을 길이축으로 굴린 상태로 세우고, 0.08 m/s 명령으로 바로 설 때까지(바로 섬 0.8 이상) 걸린 시간을 쟀다 (시드 3개, 15초).

| 시작 각도 | v7 | v8 1150회 | v8 최종 |
|---|---|---|---|
| +90° | 0.5, 0.6 s, 실패 | 0.3–0.4 s | **0.7 s** |
| +135° | 실패 | 실패 | **1.1–1.4 s** |
| 180° (완전히 뒤집힘) | 실패 | 실패 | **1.3–1.8 s** |
| −90° | 실패 | 실패 | **0.8–1.2 s** |

최종 v8은 어느 각도에서든 2초 안에 스스로 굴러 바로 서고, 그 뒤 15초 동안 약 1.2 m 전진했다. 학습 1150회 시점에는 한쪽 방향 90°에서만 회복해서 몸통 yaw 범위 확대와 바로 섬 보상 강화를 검토했는데, 학습을 끝까지 하자 그 변경 없이도 회복을 배웠다. 스크립트 롤링 보행(모든 관절을 같은 위상으로 yaw = A·sin, pitch = A·cos)으로도 kp 3에서 0.2–1.6 s 만에 바로 서는 것을 확인해, 물리적으로 쉬운 동작임은 미리 알고 있었다.

## 제어판 UI와 도구

Teraffe의 재생 UI처럼 MuJoCo 뷰어 옆에 제어판 창을 띄운다.

| 영역 | 기능 |
|---|---|
| 지형 | 7종 선택, 레벨 0–4, 적용하면 같은 종류도 새로 생성 (뷰어를 닫지 않음) |
| 운전 | 키보드(누르고 있는 동안 선형 가속, 떼면 선형 감속, Shift+←/→ 시선) / 자동(속도·방향·머리 고정), 급정지 |
| 마찰 | 축·옆 마찰을 실행 중에 바꿈 |
| 보기 | CAD 메쉬 / 충돌 캡슐 / 둘 다, 카메라 따라가기 |
| 정책 | `rl/runs`의 실험별 최신 체크포인트와 설명, 더블클릭으로 불러오기 |

```bash
rl/.venv/bin/python rl/play_ui.py                         # 제어판
rl/.venv/bin/python rl/teleop.py --checkpoint <ckpt>      # 키보드 / --joy-topic /joy
rl/.venv/bin/python rl/evaluate.py --checkpoint <ckpt> --head
```

키보드는 Teraffe처럼 X11 키 상태를 직접 읽어 "누르고 있는 동안"을 감지한다. MuJoCo 뷰어의 키 콜백은 누르는 순간만 알려 준다.
