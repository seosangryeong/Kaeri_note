    - **무엇을:** Teraffe에게 "이 속도로 앞·옆으로 가고, 이만큼 돌고, 이 높이를 유지하라"는 명령을 주고, 여러 지형과 계단 위에서 차체를 수평으로 유지하며 따라가도록 학습시켰다.
    - **결과:** 처음 보는 지형 28가지 상황에서 **한 번도 넘어지지 않았고**, 6–14.5 cm 높이의 계단을 내리막 100%, 오르막 93–100% 통과했다.
    - **실제 로봇 조건:** 바퀴 하중·접지·지형처럼 실제 로봇이 잴 수 없는 정보를 정책 입력에서 모두 빼고 다시 학습해도(exp10, 실제 로봇용 정책) 넘어짐 0, 계단 오르막 93–95%를 유지했다.
    - **정책은 무엇을 보고 수평을 잡나:** 기울기 입력을 지우면(exp11) 계단은 여전히 넘지만 경사에서는 수평을 못 잡는다. 순간적인 변화는 다리 힘·자이로로, 오래 이어지는 기울기는 IMU 기울기로 잡는다.
    - **고속 주행:** 수평 점수를 없애고 2.5 m/s로 달리게 하면, 안정 여유에 점수를 줄 때만 스스로 회전 안쪽으로 기운다(exp14, 약 2°). 명령을 갑자기 0으로 만드는 급정지에서는 세 정책 모두 앞다리를 늘려 뒤로 7–10° 젖히지만, 뒷바퀴가 0.25초 뜬다.
    - **기존 제어와 비교:** 같은 조건에서 PD 수평 제어는 평소 수평은 비슷하게 잡지만, **접지 정보가 없으면 지형에서 넘어진다** (32가지 상황 중 17가지에서 평균 8%). 강화학습은 다리 힘과 관절 움직임으로 바퀴가 뜨는 것을 알아채 넘어지지 않았고, 계단 오르막과 거친 지형의 속도 유지도 앞섰다.
    - **계단 내리막 비교 (2026-11-23 추가):** 같은 계단 전체를 내려갈 때 강화학습(exp10 실제 로봇용)은 튜닝한 PD보다 최대 피치가 약 40% 작고 피치 속도는 약 3분의 1이다. 바퀴 하중과 순간 충격은 뚜렷한 차이가 없다. 수평 유지에 결정적인 입력은 베이스 기울기였다 ([자세히](#계단-내리막-비교-피치-바퀴-하중-입력-분석-exp1619)).

## 무엇을 만들었나

- **로봇:** Teraffe의 실제 URDF로 만든 MuJoCo 모델. 바퀴 네 개가 각각 방향을 틀고(조향) 굴러가며(구동), 다리 네 개는 2단 텔레스코픽으로 길이가 바뀐다. 총 질량 약 141 kg.
- **시뮬레이터:** MuJoCo Warp로 GPU 한 장에서 로봇 4,096대를 동시에 돌렸다 (물리 1초에 200번, 제어 1초에 20번).
- **만든 것:** 명령을 따라 주행하는 강화학습 정책, 여러 지형과 진짜 계단, 계단을 실제로 넘었는지 재는 시험, 비교용 기존 수평 제어기 두 가지.

### 명령

로봇에게 주는 명령은 네 가지다. 사람이 조이스틱으로 주는 명령과 같은 형태다.

| 명령 | 범위 | 뜻 |
|---|---|---|
| 앞뒤 속도 | −1.0 ~ 1.3 m/s | 차체가 바라보는 방향 기준 |
| 옆 속도 | ±0.8 m/s | 게걸음 |
| 회전 속도 | ±1.0 rad/s | 제자리 회전도 가능 |
| 차체 높이 | 1.5 ~ 2.9 m | **네 바퀴 아래 땅의 평균 높이**에서 잰 높이 |

## 비교한 제어 방식: 정확히 무엇을 구현했나

이 기록에서는 네 가지 방식을 만들어 같은 조건에서 비교했다. **관절을 움직이는 하위 제어와 주행 계산은 네 방식이 모두 같고, 다리 길이를 정하는 부분(수평 유지)만 다르다.** 강화학습은 여기에 조향·바퀴 보정이 더해진다.

| 방식 | 한 줄 설명 |
|---|---|
| ① 수평 제어 없음 | 다리를 명령 높이에 맞는 길이로 고정 |
| ② 비선형 P 수평 제어 | 차체 기울기에 비례해 다리를 늘이고 줄임. 비례 이득이 기울기에 따라 달라짐 (Isaac Sim 통합 제어 코드) |
| ③ PD 수평 제어 | 차체 기울기와 기울기 변화 속도에 비례해 다리를 늘이고 줄임 (MuJoCo 조이스틱 제어 코드) |
| ④ 강화학습 | 신경망이 다리 길이 변화를 직접 정하고, 조향·바퀴에도 보정을 더함 |

### 네 방식이 모두 같은 부분

```
명령: 앞뒤 속도, 옆 속도, 회전 속도, 차체 높이
  │
  ├─ 주행 계산식 (역기구학) ──────▶ 바퀴마다 조향각, 바퀴 속도
  ├─ 높이 → 기본 다리 길이
  ├─ (대각 하중 보정: 바퀴 힘 사용 → 최종 비교에서는 끔)
  │
  ├─ [방식마다 다른 부분] ─────────▶ 다리마다 늘이고 줄이는 양 (+ 강화학습은 조향·바퀴 보정)
  ▼
관절 명령 (1초에 20번)
  │
  ▼
관절 서보 (시뮬레이터 안, 1초에 200번, 이득 고정, 학습 안 함)
  다리 8개 (다리마다 2단) : 위치 명령 → 위치 PD 서보   P 20000 N/m,     D 500 N·s/m
  조향 4개                 : 위치 명령 → 위치 PD 서보   P 2000 N·m/rad, D 80,  최대 100 N·m
  바퀴 4개                 : 속도 명령 → 속도 서보      20 N·m/(rad/s),        최대 60 N·m (계단 시험에서만)
```

- **관절 단계에서는 네 방식 모두 다리·조향은 위치 명령, 바퀴는 속도 명령이다.** 관절 서보의 이득은 고정이고, 어떤 방식에서도 학습하지 않는다. 바퀴 토크 한계 60 N·m는 실제 모터 사양이 없어 정한 가정값으로, 계단 시험에만 적용했다.
- **주행 계산식(역기구학):** 차체를 원하는 속도로 움직이려면 바퀴마다 어느 방향으로, 얼마나 빨리 굴러야 하는지를 기하학으로 계산한다 (식은 아래 [원리](#원리) 참고). 네 방식 모두 이 값을 쓴다.
- **대각 하중 보정:** 다리 넷이 모두 단단해서, 대각선 다리 길이가 조금만 어긋나도 한쪽 대각선 바퀴가 뜬다. 바퀴 힘을 재서 대각선 두 쌍의 힘이 같아지도록 다리를 조금씩 조절하는 기능이다. 1·2단계 학습(exp01–exp09)에서는 켰지만, 바퀴 힘은 실제 로봇에서 잴 수 없어서 **최종 비교(3단계)와 exp10에서는 네 방식 모두 껐다.**

### 방식마다 다른 부분: 다리 길이를 어떻게 정하나

세 방식(②③④)은 모두 **"다리 길이를 얼마나 빨리 늘이고 줄일지"(다리 속도)를 정하고, 이것을 쌓아서(적분해서) 다리 위치 명령을 만든다.** 무엇을 보고 다리 속도를 정하는지가 다르다.

```
다리 위치 명령 = 기본 다리 길이 + 대각 하중 보정 + 누적 다리 보정
누적 다리 보정 += 다리 속도 × 0.05초        (매 제어 주기마다)
```

| | ② 비선형 P | ③ PD | ④ 강화학습 |
|---|---|---|---|
| 입력 | 차체 roll·pitch | 차체 roll·pitch, 그 변화 속도 | 차체 속도·기울기, 관절 상태, 다리 힘, 명령 등 63개 |
| 다리 속도를 정하는 것 | 정해 둔 곡선 | P·D 식 | 학습된 신경망 |
| 다리 배분 | 앞뒤·좌우 부호만 (네 다리에 같은 크기 ±) | 바퀴 위치(앞뒤 x, 좌우 y)에 비례 | 신경망이 다리마다 따로 정함 |
| 최대 다리 속도 | 0.1 /s | 0.35 /s | 0.5 /s |
| 조향·바퀴 | 계산식 그대로 | 계산식 그대로 | 계산식 + 신경망 보정 |

**② 비선형 P:**

```
f(θ) = 0                      (|θ| ≤ 0.03°)
     = 0.005 × (θ/5°)²         (5° 이하)
     = 0.005 → 0.1 로 증가      (5°–15°)
     = 0.1                     (15° 이상)        [단위: 다리 길이/초, 부호는 θ를 따름]
다리 i 속도 = (앞다리 +1, 뒷다리 −1) × f(pitch) − (왼쪽 +1, 오른쪽 −1) × f(roll)
네 다리 평균은 0으로 맞추고, 가장 긴 다리와 짧은 다리 차이는 0.8 이하
```

**③ PD:**

```
보정 = 3.5 × 기울기 + 0.12 × 기울기 변화 속도       (roll, pitch 각각, 0.05° 아래는 무시)
다리 i 속도 = (보정_pitch × x_i − 보정_roll × y_i) / 0.97     (x_i, y_i: 바퀴의 앞뒤·좌우 위치)
(원래 코드에는 "닿은 바퀴가 3개 미만이면 멈춤, 뜬 바퀴 다리 내림" 규칙이 있지만, 접지는 잴 수 없어 최종 비교에서는 뺐다)
네 다리 평균은 0으로 맞추고, 다리 속도는 ±0.35/s, 차이는 1.6 이하
```

두 식 모두 원래 코드의 숫자를 그대로 썼다. MuJoCo 로봇에 맞게 바꾼 것은 다리 번호·방향과, 원래 코드가 가장 낮은 다리를 0까지 내리던 것을 높이 명령을 유지하도록 한 것 두 가지다.

### 강화학습은 정확히 무엇을 했나

**학습한 것은 신경망 하나다.** 입력 63개를 받아 은닉층 3개(256, 256, 128개)를 거쳐 12개 숫자를 내는 함수로, 이것을 정책이라고 부른다.

- **기존 수평 제어식의 이득을 학습한 것인가?** 아니다. 강화학습 쪽에는 PD 같은 수평 제어식이 없다. 다리 쪽에서는 신경망이 수평 제어기 자체를 대신한다.
- **보정값만 학습한 것인가?** 조향·바퀴는 그렇다. 계산식 값에 신경망이 보정을 더한다. 다리는 기본 다리 길이와 대각 하중 보정 위에서 **다리별 차이를 신경망이 전부 정한다.** 기존 방식에서는 이 다리별 차이를 수평 제어식(②③)이 정했다.
- **속도 제어인가, 위치 제어인가?** 출력마다 다르다.

| 출력 (각각 −1~1) | 출력의 뜻 | 관절로 가는 명령 |
|---|---|---|
| 다리 4개 | 다리 길이 변화 속도 = 출력 × 0.48 m/s | 쌓아서 **위치 명령** (기본 길이 + 누적 보정, 최대 ±0.48 m) |
| 조향 4개 | 보정각 = 출력 × 17° | **위치 명령** = 계산식 각도 + 보정 (±90° 안) |
| 바퀴 4개 | 보정 속도 = 출력 × 4 rad/s (약 0.4 m/s) | **속도 명령** = 계산식 속도 + 보정 (±16 rad/s 안) |

- **다리를 "위치" 대신 "속도"로 낸 이유:** 처음에는 다리 목표 길이를 직접 내도록 했는데, 신경망이 최댓값과 최솟값을 오가는 습관을 배워 다리가 1초에 20번씩 떨렸다. 속도로 바꾸자 이 문제가 사라졌다 (아래 1단계 참고).
- **정책이 보는 정보:** 차체 속도·회전 속도·기울기, 차체 높이, 관절 위치·속도, 다리에 걸리는 힘, 명령, 직전 출력, 계산식 값이다. 차체 높이는 exp09까지는 지형 기준이었고, exp10부터는 다리 관절과 기울기로 계산한 값(실제 로봇에서 잴 수 있음)이다. **지형을 직접 보지는 않는다.** 바퀴가 무엇을 밟았는지는 다리 힘과 차체 흔들림으로 느낀다. 카메라 같은 센서 정보는 쓰지 않는다.
- **학습 방법:** 시뮬레이터 안에서 로봇 4,096대를 동시에 굴리며, 잘하면 점수를 주고 못하면 깎는 보상(아래 '강화학습 세부'를 펼치면 표가 있다)을 최대화하도록 PPO라는 알고리즘으로 학습했다. 처음에는 출력에 무작위 잡음을 섞어 여러 동작을 시도하게 하고, 점점 점수가 높은 동작 쪽으로 신경망을 고친다. 비교에 쓴 정책(exp05)은 약 5.4억 번의 제어 스텝(4,096대 × 24스텝 × 5,500회)을 학습했고, 최종 계단 정책(exp09)은 여기에 계단 지형으로 3,000회를 더 학습했다.

    | 자세 | +1, −5 | 목표 자세(평소엔 수평, 회전할 땐 안쪽으로 조금)에 가까울수록 |
    | 네 바퀴 모두 접지 | +1 | |
    | 바퀴가 오래 뜸 | −2 | 0.1초 넘게 뜬 시간만 벌점 (순간적인 들림은 봐줌) |
    | 한 바퀴에 하중이 너무 적음 | −1 | 평균의 30% 미만일 때 |
    | 넘어질 위험 | −1 | 무게중심이 바퀴 네 개가 만드는 사각형 가장자리에 가까울 때 |
    | 떨림·과한 움직임 | 작은 벌점 | 출력 변화, 조향 변화, 다리 속도, 전력 |
    | 넘어짐 | −30 | |

    **넘어짐 판정:** 35° 넘게 기울거나, 차체가 땅에서 1 m 아래로 내려가거나, 20° 이상 기운 채 0.5초가 지나면 넘어진 것으로 본다. 순간적인 흔들림은 넘어짐으로 세지 않는다.

    **회전할 때 안쪽으로 기울기:** 빠르게 돌면 바깥쪽 바퀴로 무게가 쏠린다. 그래서 회전할 때는 목표 자세를 안쪽으로 조금(최대 6°) 기울였다. 차체가 높을수록 더 기울인다.

**정리하면:** 기존 방식과 강화학습은 "다리 속도를 정해 쌓아서 위치 명령으로 보낸다"는 구조가 같다. 다른 점은 셋이다. (1) 다리 속도를 식이 아니라 신경망이 정하고, (2) 차체 기울기만이 아니라 63개 상태를 보며, (3) 조향·바퀴에도 보정을 더한다.

### 원인을 가려내려고 섞어 본 조합

계단에서 강화학습이 왜 나은지 알아보려고, 신경망 출력 12개 중 **조향·바퀴 8개는 신경망 그대로 두고 다리 4개만 ③ PD(또는 ②)의 출력으로 바꾼** 조합도 시험했다 (아래 3단계).

## 1단계: 여러 지형에서 주행 배우기

### 지형과 단계별 학습

경사, 물결, 요철, 작은 둔덕, 계단(낮은 것), 턱, 이것들을 섞은 지형까지 여덟 종류를 만들었다. 처음부터 어려운 지형을 주면 배우지 못해서, **쉬운 것부터 단계적으로** 올렸다. 이것을 커리큘럼이라고 한다.

- 한 단계에서는 **한 가지만** 어렵게 한다 (지형, 속도 범위, 높이 범위 중 하나).
- 잘하면 다음 단계로 올라가고, 못하면 내려온다.
- 어려운 지형만 보다가 쉬운 것을 잊지 않도록, 4번에 1번은 낮은 단계 지형을 다시 보여 준다.

??? 단계표
    | 단계 | 지형 난이도 | 속도 범위 | 회전 범위 | 높이 범위 |
    |---|---|---|---|---|
    | 0 | 0 (거의 평지) | 30% | 30% | 15% |
    | 1 | 0 | 60% | 60% | 40% |
    | 2 | **1** | 60% | 60% | 40% |
    | 3 | 1 | **100%** | **100%** | **70%** |
    | 4 | **2** | 100% | 100% | 70% |
    | 5 | 2 | 100% | 100% | **100%** |
    | 6 | **3** | 100% | 100% | 100% |
    | 7 | **4** (가장 어려움) | 100% | 100% | 100% |

    올라가는 조건은 성공률 75% 이상, 네 바퀴 접지율(난이도별 90→75%), 넘어짐 3% 이하를 두 번 연속 지키는 것이다. 계단 학습 때는 8·9단계(난이도 5·6)를 더했다.

### 학습이 막혔던 이유 세 가지

처음에는 0단계에서 더 올라가지 못했다. 원인은 학습 방법이 아니라 대부분 **로봇 모델과 제어 구조**에 있었다. 정책을 끄고 식으로 계산한 값만으로 굴려 보니 문제가 그대로 보였다.

| 문제 | 원인 | 해결 | 효과 |
|---|---|---|---|
| 제자리 회전만 하면 바퀴가 뜸 | 시뮬레이터가 원기둥 바퀴와 지면 사이에 접촉점을 하나만 만들어서, 바퀴를 틀면 그 점이 튀었다 | 바퀴 충돌 모양을 같은 크기의 공으로 바꿈 | 네 바퀴 접지 81% → 99.9% |
| 대각선 두 바퀴가 같이 뜸 | 다리 넷이 모두 단단해서, 대각선 다리 길이가 3 cm만 어긋나도 한쪽 대각선이 들린다 (식탁 다리 하나가 짧으면 흔들리는 것과 같다) | 대각선 두 쌍의 하중 차이를 0으로 맞추는 보정을 다리에 추가 | 0% → 98.5% |
| 다리가 1초에 20번씩 떪 | 정책이 "목표 다리 길이"를 내도록 했더니, 위아래로 최대치를 오가는 습관을 배웠다 | 정책이 "다리를 늘이고 줄이는 속도"를 내도록 바꿈 | 처음으로 끝 단계까지 도달 (약 700회 학습) |

![커리큘럼 단계와 학습 중 접지율](assets/mujoco-loco-training.png)
*실험마다 몇 단계까지 올라갔는지(왼쪽)와 학습 중 네 바퀴 접지율(오른쪽). 노란 선(다리 속도 방식)에서 처음으로 끝까지 올라갔다. 학습 중 수치는 일부러 넣은 무작위 탐색이 섞여 있어 실제 성능보다 낮게 나온다.*

### 결과: 처음 보는 지형에서

학습에 쓰지 않은 **새로 만든 지형**에서 28가지 상황(평지 주행, 급회전, 높은 자세 회전, 주행 중 높이 바꾸기, 경사·요철·계단·턱·혼합 지형, 무작위 명령 등)을 128대씩 16초 동안 시험했다. 지형을 바꿔 세 번 반복했다.

| 지표 | 값 |
|---|---|
| 넘어짐 | 0회 |
| 속도 오차 / 회전 오차 / 높이 오차 | 0.056 m/s / 0.014 rad/s / 0.5 cm |
| 최대 기울기 | 8° |
| 네 바퀴 모두 접지 | 96% |
| 0.1초 넘게 뜬 바퀴가 없던 시간 | 99.7% |
| 성공률 | 99.6% |

#### 성공률은 어떻게 재나

성공률은 에피소드마다 성공·실패를 세는 것이 아니라, **매 순간(0.05초마다) 아래 다섯 조건을 동시에 지킨 시간의 비율**이다. 시나리오마다 128대를 16초씩 굴리고, 출발하는 처음 3초는 뺀다.

| 조건 | 기준 | 예시 |
|---|---|---|
| 속도 | 속도 오차 < **0.12 m/s + 명령 속도의 15%** | 0.6 m/s 명령이면 오차 0.21 m/s 이내 |
| 회전 | 회전 속도 오차 < **0.15 rad/s + 명령 회전의 15%** | 0.8 rad/s 명령이면 0.27 rad/s 이내 |
| 높이 | 높이 오차 < **8 cm** | |
| 자세 | 목표 자세와의 차이 < **5°** | 평소 목표는 수평, 회전할 때는 안쪽으로 조금 기운 자세 |
| 넘어짐 | 넘어지지 않음 | |

- 속도와 회전 오차는 **0.5초 평균**으로 본다. 지형에서 순간적으로 덜컥거리는 것까지 실패로 세지 않으려는 것이다. 높이와 자세는 순간값을 쓴다.
- 학습할 때 다음 단계로 올라갈지 판단하는 데도 같은 기준을 쓴다.
- 성공률은 **수평만이 아니라 속도까지 함께 보는 지표**다. 수평이 좋아도 속도를 못 따라가면 실패로 센다.

![실험별 접지율과 회전 오차](assets/mujoco-loco-eval.png)
*조향이 덜 돌았을 때 바퀴 속도를 줄이는 기능(exp04)을 넣으니 어려운 지형에서 접지가 좋아졌지만(왼쪽), 회전 반응이 느려졌다(오른쪽, exp04 정렬 감속). 회전 점수를 키운 exp05로도 되돌리지 못했다.*

### 지형이 생각보다 쉬웠다

결과가 너무 좋아서 지형을 다시 확인해 보니, 실제로 쉬웠다.

- 지형은 일정 간격의 점에 높이를 적은 **높이맵**으로 만든다. 점 간격이 15 cm라서, 9 cm 계단도 15 cm 길이의 비탈처럼 매끄러웠다.
- 요철도 굴곡 간격이 2.4 m라 완만한 언덕에 가까웠다.

점 간격을 7.5 cm로 줄이고 지형을 더 크게 만들어 다시 시험했다. 넘어지지는 않았지만 촘촘한 요철과 계단에서 접지율이 크게 떨어졌다. 그래서 **진짜 계단**을 따로 만들기로 했다.

![어려운 지형 시험](assets/mujoco-loco-hard-probe.png)
*지형 크기를 키울수록(가로축) 네 바퀴 접지율이 어떻게 변하는지. 넘어짐은 모두 0이었다.*

## 2단계: 진짜 계단 오르기

### 높이맵으로는 진짜 계단이 안 된다

높이맵은 점과 점 사이를 비스듬한 면으로 잇는다. 그래서 계단의 **수직 벽이 항상 비탈이 된다.**

| 점 간격 | 12.5 cm 계단의 실제 모양 | 문제 |
|---|---|---|
| 15 cm | 40° 비탈 | 계단이 아니라 비탈 |
| 7.5 cm | 59° 비탈 | 여전히 비탈 |
| 2.5 cm | 79° 거의 벽 | 바퀴가 벽에 닿는 순간 **로봇이 튀어 오름** (시뮬레이터 오류) |

점 간격을 2.5 cm로 줄이자 거의 수직이 되었지만, 이번에는 바퀴가 벽에 닿을 때 시뮬레이터 계산이 튀면서 로봇이 공중으로 떴다. 이 상태에서는 높은 계단도 "통과"로 나왔는데, 실제로는 오류로 점프한 것이었다.

![높이맵 계단과 박스 계단 비교](assets/mujoco-stairs-artifact.png)
*정책 없이 식으로만 첫 단을 오를 때 앞바퀴 높이(파란 선)와 바퀴가 받는 힘(주황 막대). 왼쪽 높이맵 계단에서는 힘이 0이 되며 공중으로 떴다가 넘어졌다. 오른쪽 박스 계단에서는 힘을 유지한 채 모서리를 타고 올라갔다.*

**해결:** 계단의 한 단 한 단을 **상자(박스)** 로 쌓았다. 상자와 공(바퀴)의 충돌은 정확하게 계산되므로 진짜 수직 벽이 된다. 로봇 4,096대가 각자 다른 계단(위치, 방향, 단 높이)을 쓰도록 했다.

| 계단 종류 | 내용 |
|---|---|
| 박스 계단 | 몇 단 올라가서 평평한 층계참을 지나 다시 내려온다. 단 높이 6–9 cm(난이도 4)에서 9.6–14.5 cm(난이도 6)까지. 절반은 단 높이가 같고, 절반은 들쭉날쭉하다 |
| 울퉁불퉁 + 계단 | 계단 주변에 촘촘한 요철 |
| 좌우 높이차 | 바닥에 판을 여러 장 깔아, 왼쪽·오른쪽 바퀴가 서로 다른 높이를 밟게 했다 |

![계단 오르막](assets/mujoco-stairs-up.jpg)
*앞바퀴는 단 위, 뒷바퀴는 아직 아래 바닥.*

**현실적인 한계:** 바퀴는 반지름(9.6 cm)보다 조금 높은 단까지는 모서리를 타고 오를 수 있다. 바퀴를 굴리는 힘이 모서리에서 바퀴를 위로 밀어 주기 때문이다. 하지만 마찰이 충분해야 하고, 이론상 약 15–16 cm가 한계다. 그래서 계단은 **14.5 cm까지만** 만들었다. 바퀴 모터 토크는 실제 사양이 없어서 바퀴당 60 N·m로 가정했다.

### 계단을 "진짜로 넘었는지" 재기

넘어지지 않고 버틴 것과 계단을 넘은 것은 다르다. 그래서 계단 시험을 따로 만들었다.

- 계단 바로 앞(내리막은 꼭대기)에서 출발해 계단 쪽으로 가라고 명령한다.
- **마지막 단을 지나 차체 길이만큼(1.7 m) 더 갔을 때만** 성공으로 센다.
- 시간 안에 못 넘으면 "멈춤"으로 세고, 진행 속도가 명령의 25% 아래로 떨어진 시간 비율도 잰다.
- 같은 정책을 다시 재도 결과가 꽤 흔들려서(128번 시험할 때 ±3%), 최종 비교는 **1,024번씩** 시험했다.

### 학습 전 시험

계단을 배운 적 없는 1단계 정책(exp05, 계단 학습 전 기준)도 이미 계단을 꽤 잘 넘었다.

| 단 높이 (최대) | 8.7 cm | 12.0 cm | 12.8 cm, 단이 더 많음 | 내리막 (전체) |
|---|---|---|---|---|
| 식으로만 (정책 없음) | 100% | 98% | 68% | 98–100% |
| 1단계 정책 (exp05) | 100% | 100% | 91% | 100% |

![식으로만 vs 정책](assets/mujoco-stairs-feasibility.png)
*식으로만 굴리면 12 cm까지는 넘지만 차체가 15–22° 기운다. 정책은 같은 계단을 3–8° 기울기로 넘는다.*

### 계단 학습 실험

모두 exp05(계단 학습 전 기준)에서 이어서 학습했고, 실험마다 **한 가지만** 바꿨다.

| 실험 | 바꾼 것 | 결과 |
|---|---|---|
| exp07 (계단 그대로 학습) | 계단 지형으로 그대로 학습 | 오히려 나빠짐. 들쭉날쭉한 계단 95% → 87% |
| exp08 (지형 높이 입력) | + 바퀴 주변 지형 높이를 보여 줌 (깊이 카메라·라이다로 얻을 수 있는 정보) | 나아지지 않음 (90%) |
| **exp09 (계단 높이 제한)** | exp07과 같고, **계단 높이만 14.5 cm 이하로 제한** | **가장 어려운 오르막 99.9%, 들쭉날쭉한 오르막 100%** |

![최종 계단 비교](assets/mujoco-stairs-final.png)
*1,024번씩 시험한 계단 통과율(왼쪽, 막대 위 선은 오차 범위)과 멈춰 있던 시간(오른쪽). 계단 높이를 제한한 exp09(계단 높이 제한)가 가장 좋다.*

**왜 계단 학습이 오히려 나빠졌나:** 들쭉날쭉한 계단을 만들 때 단 높이가 최대 **17.4 cm**까지 나오고 있었다. 바퀴로는 오를 수 없는 높이다. 멈춘 경우를 살펴보면 뒷바퀴는 모터 힘을 다 쓰고 앞바퀴는 헛돌고 있었다. 정책이 "아무리 밀어도 안 되는" 경험을 반복하면서 오히려 덜 미는 쪽으로 배운 것으로 보인다. 오를 수 있는 높이로 제한하자 바로 좋아졌다.

![계단 내리막](assets/mujoco-stairs-down.jpg)
*내리막은 모든 정책이 100% 통과했다.*

### 최종 정책 (exp09 계단 높이 제한, exp10 실제 로봇용)

| 항목 | exp05 (계단 학습 전 기준) | **exp09 (계단 높이 제한)** | **exp10 (실제 로봇용)** |
|---|---|---|---|
| 가장 어려운 계단 오르막 (1,024번) | 95.5% | **99.9%** | 95.3% |
| 들쭉날쭉한 계단 오르막 (1,024번) | 94.5% | **100%** | 92.5% |
| 계단 시나리오 13가지 평균 | 98.3% | **100%** | 98.4% |
| 계단 위 최대 기울기 | 9.3° | **6.5°** | 9.1° |
| 기존 상황 성공률 / 넘어짐 | 99.1% / 0 | 99.1% / 0 | 99.1% / 0 |
| 기존 상황 속도 오차 | 0.059 m/s | 0.065 m/s | 0.067 m/s |

exp09(계단 높이 제한)는 계단을 가장 잘 넘지만, 학습 중에 바퀴 힘으로 대각 다리를 보정하는 기능과 지형 기준 높이를 썼다. 이 둘은 실제 로봇에서 잴 수 없어서, 빼고 다시 학습한 exp10(실제 로봇용)이 **실제 로봇에 옮길 정책**이다. 계단 오르막이 4–8%p 낮아졌고, 나머지는 거의 같다.

## 3단계: 강화학습 vs 기존 수평 제어

강화학습이 정말 필요한지 확인하려고, [비교한 제어 방식](#비교한-제어-방식-정확히-무엇을-구현했나)에서 설명한 네 방식을 같은 지형, 같은 명령, 같은 시험으로 비교했다.

**모든 방식이 실제 로봇에서 잴 수 있는 정보만 쓰도록 맞췄다.**

| 빼낸 정보 | 쓰던 곳 | 이유 |
|---|---|---|
| 바퀴 법선력 | 대각 하중 보정 (네 방식 공통) | 바퀴마다 하중 센서가 없으면 알 수 없다 → 네 방식 모두 끔 |
| 바퀴 접지 여부 | PD 원래 코드의 안전 규칙 (닿은 바퀴가 3개 미만이면 멈춤, 뜬 바퀴 다리 내림) | 알 수 없다 → 뺌 |
| 지형 기준 차체 높이 | 강화학습 입력 | 지형을 알아야 한다 → 다리 관절과 기울기로 계산한 높이로 바꿈 |

강화학습은 이 조건으로 다시 학습한 **exp10**을 썼다. 바퀴 힘·접지·지형은 학습 중 행동을 평가하는 크리틱만 보고, 실제로 로봇을 움직이는 정책은 IMU(기울기·회전 속도), 관절 상태, 다리 구동기 힘, 명령만 본다.

### 지형에서: 차체 수평 비교

![실제 센서 조건에서 지형 수평 비교](assets/mujoco-real-terrain.png)
*위: 평균 기울기. 가운데: 최대 기울기 (35°가 넘어짐 판정). 아래: 16초 동안 넘어진 로봇 비율. 128대씩, 처음 보는 지형.*

| 지표 (32가지 상황, 기울기는 지형 시나리오만 평균) | 강화학습 (exp10 실제 로봇용) | PD | 비선형 P | 수평 제어 없음 |
|---|---|---|---|---|
| **지형 위 평균 기울기** | **1.1°** | 1.2° | 3.8° | 5.2° |
| **최대 기울기** | **8°** | 35° (넘어짐) | 23° | 33° |
| **넘어진 시나리오** | **0 / 32** | **17 / 32** (평균 8%의 로봇이 넘어짐) | 0 / 32 | 3 / 32 |
| 네 바퀴 접지 | **96%** | 82% | 86% | 85% |
| 속도 오차 | **0.07 m/s** | 0.17 m/s | 0.11 m/s | 0.11 m/s |
| 성공률 | **99%** | 81% | 76% | 72% |

- **평소 수평은 PD와 강화학습이 비슷하다** (평균 1.1–1.2°). 평지와 완만한 지형에서는 PD가 조금 더 수평이기도 하다.
- **하지만 접지 정보가 없으면 PD는 넘어진다.** 경사, 턱, 계단, 혼합 지형에서 시나리오마다 5–14%의 로봇이 넘어졌다. 바퀴 하나가 뜨면, PD는 그것을 모르고 기울기만 보고 계속 다리를 움직이다가 오히려 차체를 넘긴다. 원래 코드의 접지 규칙이 이것을 막는 안전장치였다. PD를 실제 로봇에 쓰려면 바퀴 하중 센서 같은 접지 감지가 필요하다.
- **비선형 P는 넘어지지 않지만 느리다.** 5° 아래에서는 다리를 아주 천천히 움직이도록 만들어져 있어서, 경사에서 6–8°까지 기운 채로 달린다.
- **강화학습은 같은 정보로 넘어지지 않는다.** 바퀴가 뜨는 것을 다리 힘과 관절 움직임으로 알아채도록 배웠기 때문이다 (아래 [분석](#분석-정책은-계단을-어떻게-내려가나)). 최대 기울기 8°, 넘어짐 0.

| 지표 | 강화학습 (exp10 실제 로봇용) | PD | 비선형 P | 수평 제어 없음 |
|---|---|---|---|---|
| 가장 어려운 오르막 | **93%** | 79% | 84% | 80% |
| 들쭉날쭉한 오르막 | **86%** | 67% | 67% | 67% |
| 높은 자세(2.8 m) 오르막 | **100%** | 86% | 78% | 83% |
| 내리막 | 100% | 100% | 100% | 100% |
| 멈춰 있던 시간 (13가지 평균) | **8%** | 20% | 18% | 18% |

계단에서도 같은 결과다. 평균 기울기는 PD가 조금 낮지만 최대 기울기는 35°(넘어짐 직전)까지 가고, 오르막 통과율은 강화학습이 9–22%p 높다.

### 계단 오르기에서 강화학습이 앞서는 이유

첫 비교에서 조향·바퀴는 강화학습에 맡기고 **다리만 PD로 바꿔 봤더니**, 계단 통과율이 PD 수준(80%)으로 떨어졌다 (아래 참고 상자의 그래프). 앞바퀴가 단에 걸려 올라가면 차체 앞이 들린다. PD는 이것을 수평으로 되돌리려고 **앞다리를 바로 줄인다.** 그러면 앞바퀴가 단 모서리를 누르는 힘이 빠져서 올라가지 못한다. 강화학습은 오르는 동안 **조금 기울어지는 것을 허용하고(평균 2°, 최대 8°)** 다리와 바퀴를 같이 써서 넘어간다.

??? 참고: 실제 로봇이 잴 수 없는 정보가 들어간 첫 비교 (강화학습 exp05 계단 학습 전 기준, 바퀴 힘 기반 대각 보정 켬, PD는 접지 정보 사용)
    **지형에서**

    ![지형에서 수평 제어 비교](assets/mujoco-leveling-terrain.png)
    *왼쪽: 평균 기울기(낮을수록 수평). 오른쪽: 속도·높이·자세를 동시에 지킨 시간 비율.*

    | 지표 (37가지 상황 평균) | 강화학습 | PD | 비선형 P | 없음 |
    |---|---|---|---|---|
    | 평균 기울기 | 0.85° | **0.43°** | 2.34° | 3.16° |
    | 최대 기울기 | 7.8° | **5.9°** | 14.9° | 31.7° |
    | 네 바퀴 접지 | 96% | 96% | 97% | 97% |

    | 성공률 | **99%** | 90% | 82% | 79% |
    | 넘어짐 | 0 | 0 | 0 | 0 |

    - **수평 맞추기는 PD가 더 잘한다.** 강화학습은 회전할 때 일부러 안쪽으로 조금 기울이기 때문에 기울기 숫자가 조금 크다.
    - **성공률 차이는 속도 때문이다.** 성공률은 속도까지 함께 보는 지표다([성공률은 어떻게 재나](#성공률은-어떻게-재나)). 거친 지형에서 PD 쪽은 바퀴 보정이 없어서 속도가 떨어진다. 예를 들어 "가장 거친 요철"에서 PD의 기울기는 0.5°로 강화학습과 같았지만, 속도 오차 때문에 성공률은 76%였다(강화학습 100%). **수평 성능만 비교하려면 성공률보다 기울기를 보는 것이 맞다.**
    - **자세 목표가 강화학습에 맞춰져 있다.** 자세 오차는 "회전할 때 안쪽으로 조금 기운 자세"를 목표로 잰다. 수평을 목표로 하는 PD와 비선형 P는 회전 시나리오에서 그만큼(보통 1–3°) 오차가 생겨 조금 불리하다. 5° 기준에 비하면 작아서, 성공률 차이는 대부분 속도에서 나온다.
    - 비선형 P 방식은 5° 아래에서 다리를 아주 천천히 움직이도록 만들어져 있어서, 경사와 요철에서 4–7° 기울기가 남았다. 정지 상태에서 천천히 수평을 잡는 데는 맞지만, 주행 중에는 따라가지 못한다.

    **계단에서**

    *왼쪽: 계단 통과율. 오른쪽: 계단 위 평균 기울기. "RL 바퀴 + PD 다리"는 조향·바퀴는 강화학습, 다리만 PD로 바꾼 조합이다. 조합 결과는 같은 조건(시드 2026, 512번)으로 따로 잰 것이라 강화학습 자체 값이 91–94%로 조금 다르다.*

    계단에서는 강화학습이 확실히 앞선다. 이유를 알아보려고 조향·바퀴는 강화학습에 맡기고 **다리만 PD로 바꿔 봤다.** 그러자 통과율이 PD 수준(80%)으로 떨어졌다.

    앞바퀴가 단에 걸려 올라가면 차체 앞이 들린다. PD는 이것을 수평으로 되돌리려고 **앞다리를 바로 줄인다.** 그러면 앞바퀴가 단 모서리를 누르는 힘이 빠져서 올라가지 못한다. 강화학습은 오르는 동안 **조금 기울어지는 것을 허용하고(평균 2°, 최대 8°)** 다리와 바퀴를 같이 써서 넘어간다.

## 분석: 정책은 계단을 어떻게 내려가나

계단 내리막에서 차체를 거의 수평으로 유지하는 이유를 알아보려고, 앞바퀴가 첫 단 모서리에 닿는 순간을 0초로 맞춰 60번의 내리막을 평균했다 (단 높이 약 12 cm, 0.5 m/s).

![계단 내리막 분석](assets/mujoco-descent-analysis.png)
*① 앞바퀴 하중과 앞다리 힘, ② 정책의 다리 출력, ③ 차체 앞뒤 기울기. 실선은 exp09(계단 높이 제한), 점선은 지형 기준 높이 입력을 뺀 exp10(실제 로봇용).*

| 시간 | 일어나는 일 | 차체 기울기 | 정책 출력 |
|---|---|---|---|
| 0 s 이전 | 평지 주행 | −0.3° | 다리 출력 ≈ 0 |
| **+0.1 s** | 앞바퀴가 모서리를 넘음. 앞바퀴 하중 346 → 159 N, **앞다리 힘 53 → −9 N** | **−0.2° (거의 그대로)** | 반응 시작 |
| **+0.2 s** | 앞바퀴가 허공에 뜸 (하중 0) | +0.5° | **앞다리 늘림 + 뒷다리 줄임** (최대 속도의 50–70%) |
| +0.3 s | 앞바퀴가 아래 단에 착지 (순간 하중 약 880 N) | +1.3° (최대) | 앞다리 +0.8, 뒷다리 −1.0 |
| +0.4 s 이후 | 네 바퀴 모두 접지 | 0.6–0.9° | **출력이 다시 0 근처**, 바뀐 다리 길이를 유지 |

이 데이터에서 읽을 수 있는 것은 세 가지다.

- **기울기가 아니라 다리 힘이 먼저 신호를 준다.** 정책이 움직이기 시작한 0.1–0.2초에 차체 기울기는 0.5°도 바뀌지 않았다. 대신 바퀴가 허공에 뜨면서 앞다리에 걸리던 힘이 먼저 빠진다. 정책은 이 힘 변화를 보고 기울기가 커지기 전에 반응한다.
- **앞다리만이 아니라 뒷다리도 같이 쓴다.** 앞다리를 약 4 cm 늘리고 뒷다리를 약 6 cm 줄여서 12 cm 단차의 대부분을 다리 길이 차이로 흡수했다. 나머지 약 2 cm는 차체가 1° 정도 기우는 것으로 흡수했다. 한쪽만 크게 움직이지 않아 차체 높이도 거의 그대로다.
- **착지하면 멈추고 유지한다.** 다리 힘이 정상(약 60 N)으로 돌아오면 출력이 0 근처로 돌아가고, 바뀐 다리 길이가 그대로 유지된다. 토크를 직접 조절하는 것이 아니라, 다리 위치 명령을 바꾼 뒤 멈추는 방식이다. 실제 토크는 관절 서보가 낸다. 다음 단과 뒷바퀴가 모서리를 지날 때도 같은 동작을 반복한다.

!!! warning "정정 (2026-11-23): "기울기가 커지기 전에 반응한다"는 해석은 과했다"
    위 표와 해석은 기록을 위해 그대로 둔다. 0.1초 간격의 평균만 보고 순서를 판단했고, 입력을 빼 보는 실험이 없었다. 이후 로봇별로 다시 재니 exp10(실제 로봇용)은 **다리 힘 변화 53 ms → 기울기 시작 110 ms → 다리 반응 156 ms** 순서였고, 기울기보다 다리가 먼저 움직인 경우는 7%였다. 또 다리 힘을 빼고 재학습한 exp17(다리 힘 뺌)도 반응 시간과 최대 기울기가 대조군과 비슷했다. 따라서 이 동작을 **"선제적"이라고 부르거나 다리 힘 때문이라고 단정할 수 없다.** 정확한 표현은 "지면을 잃은 뒤 빠르게 반응해 기울기를 작게 유지한다"이다. 자세한 비교는 [계단 내리막 비교](#계단-내리막-비교-피치-바퀴-하중-입력-분석-exp1619)에 있다.

**지형을 미리 안 것은 아닌가?** exp09(계단 높이 제한)는 입력 중 차체 높이가 "바퀴 아래 지형 기준 높이"라서, 앞바퀴가 모서리를 넘는 순간 이 값이 약 6 cm 갑자기 커진다. 이것을 단서로 썼을 수 있다. 그래서 이 입력을 다리 관절과 기울기로 계산한 높이(실제 로봇에서 잴 수 있는 값)로 바꾼 exp10으로 같은 분석을 했다. 반응 시점, 출력 크기, 최대 기울기(1.3° → 1.0°)가 거의 같았다. **이 동작은 지형 정보가 아니라 다리 힘과 관절 상태 같은 자기 몸 감각만으로 배운 것이다.** 실제 로봇에서도 다리 구동기 힘(모터 전류)을 잴 수 있으면 같은 방식이 가능하다.

**내리막이 오르막보다 쉬운 이유:** 내리막은 중력이 도와서, 바퀴가 뜨는 순간 다리만 내려 주면 된다. 신호(다리 힘이 빠짐)가 분명하고 동작도 단순하다. 오르막은 바퀴로 모서리를 밀어 올라가야 해서 힘이 필요하고, 수평을 너무 빨리 맞추면 오히려 누르는 힘이 빠진다. 그래서 기존 PD 제어와의 차이도 오르막에서 크게 났다.

## 분석: 기울기 입력 없이도 수평을 잡을까 (exp11 기울기 입력 뺌)

정책 입력에서 **차체 기울기(중력 방향 3개 값)를 0으로 지우고** 학습을 이어 했다. 회전 속도(자이로), 다리 관절, 다리 힘, 바퀴 속도는 그대로 준다. 비평가(학습 때만 쓰는 평가 신경망)는 기울기를 계속 본다. 실제 로봇에는 IMU가 있으니 실용 목적이 아니라, **"정책이 수평을 잡을 때 무엇을 보나"**를 알아보는 실험이다. exp10 최종 정책에서 시작해 2000번 더 학습했다.

**빼자마자 무너졌다.** 기울기를 지운 직후 평균 기울기가 3.5°에서 24°로 커지고, 69–85%가 넘어졌다. 학습 단계도 가장 쉬운 단계까지 내려갔다. exp10은 수평 유지에 기울기 입력을 크게 기대고 있었다는 뜻이다. 다시 학습하자 쉬운 지형에서는 약 900번 만에 0.8°까지 회복했지만, 2000번이 끝날 때 학습 단계는 1(5단계 중 둘째)에 머물렀다.

같은 시험(기존 지형 28개 + 어려운 지형 8개 + 박스 계단 13개)으로 exp10(실제 로봇용)과 비교했다.

![기울기 입력 유무 비교](assets/mujoco-no-orientation.png)
*같은 시험 조건에서 exp10(실제 로봇용)과 exp11(기울기 입력 뺌). 경사는 오르막·회전·옆으로 가로지르기 3가지 평균.*

| | exp10 (기울기 입력 있음) | exp11 (기울기 입력 없음) | 참고: 수평 제어 없음 |
|---|---|---|---|
| 평지 평균 기울기 | 1.2° | **0.8°** | 0.0° |
| 경사 평균 기울기 | 1.4° | **8.1°** | 9.0° |
| 경사 성공률 | 100% | **29%** | — |
| 기존 지형 전체 성공률 | 99% | 82% | — |
| 계단 통과율 (13개 평균) | 98% | 94% | — |
| 계단 위 평균 / 최대 기울기 | 1.2° / 9° | 4.7° / 27° | — |
| 넘어짐 | 0 | 0 | — |

결과는 예상대로 갈렸다.

- **경사에서는 거의 수평을 못 잡는다.** 경사 위 기울기 8.1°는 다리를 전혀 안 쓰는 경우(9.0°)와 거의 같다. 경사에 서 있으면 차체가 일정한 각도로 계속 기울어 있을 뿐, 다리 힘이나 회전 속도에는 변화가 없다. 기울기 입력이 없으면 **"지금 얼마나 기울었나"를 알 방법이 없다.** 다리 힘의 앞뒤 차이로 짐작할 수는 있지만 학습하지 못했다.
- **평지와 계단 통과는 대체로 유지된다.** 평지에서는 오히려 더 수평이다 (평지에서는 "늘 수평"이라고 가정해도 맞기 때문). 계단에서도 94%는 통과하고 넘어짐도 0이다. 앞의 내리막 분석처럼 **바퀴가 뜨고 닿는 순간은 다리 힘과 자이로로 알 수 있어서**, 단을 넘는 동작은 기울기 입력 없이도 된다. 다만 넘은 뒤 원래 자세로 돌아오는 기준이 없어서 계단 위 기울기가 4배쯤 커졌다.

**정리:** 정책은 두 가지 신호를 나눠 쓴다. **순간적인 변화(바퀴가 뜨거나 걸림)는 다리 힘·자이로로**, **오래 지속되는 기울기(경사)는 기울기 입력으로** 잡는다. 실제 로봇에서는 IMU 기울기 입력이 꼭 필요하다. 경사가 느리게 변하는 상황이 주로 문제가 되므로, IMU의 기울기 추정 지연이나 오차에 강한지는 따로 확인할 만하다.

## 고속 주행: 다리 길이로 자세를 바꿔 안정성을 얻나 (exp12–14)

쇼트트랙 선수는 빠르게 돌 때 몸을 회전 안쪽으로 눕혀서 원심력에 버틴다. 이 로봇도 다리 길이를 바꿀 수 있으니, **바깥 다리를 늘리고 안쪽 다리를 줄여서** 차체를 안쪽으로 기울일 수 있다. 급정지할 때는 앞다리를 늘려 뒤로 젖힐 수 있다. 그동안의 정책은 "차체 수평" 점수를 받았기 때문에 이런 자세를 쓸 이유가 없었다. 그래서 수평 점수를 없애고, 빠르게 달리면서 몸이 어떻게 바뀌는지 봤다.

### 조건

| | 기존 (exp10 실제 로봇용) | 고속 실험 (exp12–14) |
|---|---|---|
| 전진 속도 명령 | 최대 1.3 m/s | 최대 4 m/s |
| 회전 | 1 rad/s | 2 rad/s |
| 가속·감속 | 1 m/s² | 4 m/s² (급정지 포함) |
| 바퀴 속도 상한 | 16 rad/s | 45 rad/s |
| 지형 | 여러 지형 | 넓은 평지 |

센서 조건은 exp10과 같고(실제 로봇이 잴 수 있는 것만), 높이 명령은 1.5–2.9 m에서 무작위로 바뀐다. 세 실험의 차이는 점수 설계뿐이다.

| | 수평 점수 | 넘어질 위험 벌점 | 높이 점수 |
|---|---|---|---|
| exp12 고속·수평 점수 없음 | 없음 | 위험할 때만 (여유 0.4 미만) | 약하게 (낮춰도 됨) |
| exp13 고속·수평 점수 있음 (대조군) | 있음. 목표는 회전 시 정해 준 각도만큼 안쪽으로 (최대 6°) | 위험할 때만 | 강하게 |
| exp14 고속·안정 여유 점수 | 없음 | **항상** (여유가 넓을수록 좋음) | 강하게 (차체를 낮춰서 안정을 얻지 못하게) |

**넘어질 위험 여유**는 무게중심에 가속도의 영향을 더한 점(ZMP)이 네 바퀴가 이루는 사각형 안 어디에 있는지를 뜻한다. 1이면 한가운데, 0이면 가장자리, 음수면 밖(넘어지기 시작)이다. 회전하면 원심력 때문에 이 점이 바깥으로 밀린다. 차체를 안쪽으로 기울이면 다시 안으로 들어온다.

### 먼저 알게 된 것: 최고 속도는 약 2.8 m/s

4 m/s까지 명령했지만 어느 정책도 2.8 m/s를 넘지 못했다. 바퀴 관절의 감쇠(2 N·m·s/rad)와 바퀴 모터 토크 상한(60 N·m, 가정값)이 30 rad/s에서 같아지기 때문이다. 바퀴 반지름이 9.6 cm라서 약 2.9 m/s가 한계다.

명령이 이보다 빠르면 정책은 "계속 가속 중"인 상태로 남는다. 이때는 **앞으로 7–12° 숙인 채 달렸다.** 2.5 m/s 이하에서는 거의 수평(±2°)이었다. 그래서 자세 평가는 모두 2.5 m/s 이하에서 했다. 더 빠른 주행을 보려면 실제 바퀴 모터의 토크 사양이 필요하다.

### 결과

![고속 주행 자세](assets/mujoco-agile-posture.png)
*2.5 m/s로 직진하다 1 rad/s로 좌회전할 때의 옆 기울기와 바깥·안쪽 다리 길이 차이, 2.5 m/s에서 급정지할 때의 앞뒤 기울기. 128번 평균.*

|---|---|---|---|
| 옆 기울기 (+ 안쪽) | **−1.4°** (바깥) | +4.0° | **+2.0°** |
| 바깥 − 안쪽 다리 길이 | −2.2 cm | +6.5 cm | +3.2 cm |
| 넘어질 위험 여유 | 0.60 | 0.71 | 0.67 |
| 차체 높이 | 2.20 m | 2.21 m | 2.21 m |
| 넘어짐 | 0 | 0 | 0 |

| 2.5 m/s → 정지 (평소처럼 4 m/s²로 명령을 줄임) | exp12 수평 점수 없음 | exp13 수평 점수 있음 | exp14 안정 여유 점수 |
|---|---|---|---|
| 정지 시간 / 거리 | 0.60 s / 0.74 m | 0.61 s / 0.77 m | 0.60 s / 0.73 m |

- **수평 점수만 없애면 안쪽으로 기울지 않는다 (exp12 고속·수평 점수 없음).** 오히려 원심력에 밀려 바깥으로 1.4° 기운다. 넘어질 위험 벌점은 여유가 0.4 아래일 때만 붙는데, 이 로봇은 141 kg 중 약 118 kg이 다리라 무게중심이 낮다. 그래서 2.5 m/s 회전에서도 여유가 약 0.6이라 **기울어도 얻는 점수가 없었다.**
- **안정 여유에 항상 점수를 주면 스스로 안쪽으로 기운다 (exp14 고속·안정 여유 점수).** 높이는 명령대로 유지한 채 바깥 다리를 3 cm 늘려 안쪽으로 2° 기울었고, 여유가 0.60에서 0.67로 넓어졌다. 회전 초반에는 4°까지 기울었다가 줄어들고 다시 늘어나는 등 아직 일정하지 않다.
- **대조군 exp13(고속·수평 점수 있음)의 4°는 "정해 준 목표"를 따른 것이다.** 정책이 스스로 찾은 자세가 아니다. 그래도 4° 기울였을 때 여유가 0.71로 가장 넓어서, 안쪽으로 기우는 것이 실제로 안정성에 도움이 된다는 것은 확인된다.
- **쇼트트랙만큼 크게 기울지는 않는다.** 무게중심이 낮아서 같은 각도를 기울여도 무게중심이 옆으로 옮겨 가는 거리가 짧다. 그래서 얻는 여유에 비해 다리를 크게 움직이는 비용(다리 속도·동작 변화 벌점)이 크다. 사람처럼 무게중심이 높은 몸이어야 크게 눕는 것이 이득이다.
- **평소 정지에서는 자세를 거의 바꾸지 않는다.** 명령이 4 m/s²로 줄어드는 평소 정지는 세 정책 모두 0.6초, 약 0.75 m 만에 서고, 앞뒤 기울기 변화는 1° 미만이다. 이 정도 감속에서는 여유가 0.9 이상 남는다. exp14(안정 여유 점수)는 일정한 속도로 달리는 동안 서서히 뒤로 4°까지 젖혀지는데, 이 자세는 여유를 오히려 줄여서(0.97 → 0.88) 이유를 설명하지 못했다.

### 급정지: 명령을 갑자기 0으로 하면

평소 정지와 달리, 달리는 중에 속도 명령을 **한 번에 0으로** 바꿨다. 학습 때는 명령이 항상 4 m/s²로 줄어들었으므로, 정책이 한 번도 본 적 없는 상황이다. 2.5 m/s에서 64번 평균했다.

![급정지](assets/mujoco-sudden-stop.png)
*실선은 급정지, 점선은 평소 정지. 0초에 정지 명령.*

세 정책 모두 같은 방식으로 반응했다.

1. **0.05초 안에 앞다리를 늘리고 뒷다리를 줄인다.** 다리 출력이 최대치까지 올라간다. 앞다리가 뒷다리보다 9–23 cm 길어지고 차체가 뒤로 3–10° 젖혀진다. 수평 점수가 없는 exp12·exp14가 크게, 수평 점수가 있는 exp13이 작게 젖힌다.
2. **그동안 뒷바퀴가 0.25초 동안 뜬다** (하중 0). 뒷다리를 빠르게 줄이면서 바퀴를 들어 올린 것이다.
3. **0.3초에 뒷바퀴가 다시 땅에 닿으며** 순간 하중이 1,100–1,200 N까지 올라가고, 이후 젖힌 자세를 천천히 푼다.

이 동작이 실제로 도움이 되는지 보려고, 같은 급정지에서 **다리만 움직이지 못하게 고정**하고 바퀴·조향은 정책이 그대로 하게 했다.

| 2.5 m/s 급정지 | 정책이 다리도 씀 | 다리 고정 |
|---|---|---|
| 차체가 멈출 때까지 (exp12 / exp13 / exp14) | 0.31 / 0.36 / 0.32 m | 0.51 / 0.50 / 1.37 m* |
| 뒷바퀴가 뜬 시간 | 0.24–0.27 s | 0.02–0.05 s |
| 넘어질 위험 여유 최저값 | 0.31–0.42 | 0.40–0.52 |
| 넘어짐 | 0 | 0 |

*exp14를 다리 고정으로 돌린 1.37 m는 다른 둘과 많이 달라서 따로 살펴봐야 한다 (아직 원인을 확인하지 않음).*

- **차체는 더 빨리 멈춘다.** 앞다리를 늘려 차체를 뒤로 젖히면 차체가 바퀴보다 먼저 뒤로 물러나서, 차체 기준 정지 거리가 0.5 m에서 0.3 m로 줄었다.
- **하지만 더 안전해진 것은 아니다.** 뒷바퀴가 뜨고 앞바퀴 둘로만 버티는 시간이 생겨서, 넘어질 위험 여유는 오히려 0.1 정도 줄었다. 사람이 급정거할 때 몸을 뒤로 젖혀 버티는 것과 겉모습은 비슷하지만, 이 로봇에서는 뒷바퀴를 들어 올리는 비용이 따른다.
- 학습 중에 본 적 없는 명령이라 다리 출력이 최대치에 붙는다. 실제 로봇에서 급정지를 쓰려면 학습 때 급정지 명령도 섞어서, 뒷바퀴를 들지 않고 서는 법을 따로 배우게 해야 한다.

### exp15 고속·조건부 수평: 직진에서는 다시 수평으로

수평 점수를 없앤 exp14(고속·안정 여유 점수)는 평범한 직진에서도 차체가 기울었다. exp15는 회전이나 가감속이 없을 때는 수평을 요구하고, 그런 동작 중에만 수평 조건을 풀어 준다. 직진 기울기는 4.86°에서 **1.02°**로 줄었고 속도 오차도 0.162에서 0.058 m/s로 줄었다. 다만 같은 고속 평지 시험에서 PD의 직진 기울기는 0.02°였고, 회전 안정 여유도 PD 0.836, exp15 0.814로 **PD보다 낫지 않았다.**

## 계단 내리막 비교: 피치, 바퀴 하중, 입력 분석 (exp16–19)

**질문:** 강화학습은 계단을 내려갈 때 기존 제어보다 차체를 얼마나 덜 흔드는가, 바퀴에 걸리는 충격은 어떤가, 그리고 어떤 입력 덕분인가.

**시험 조건:** 레벨 6 박스 계단(단 높이 11.7–12.2 cm, 5–6단), 전진 0.5 m/s, 차체 높이 2.2 m. 평가 시드마다 계단 하나를 고르고 **모든 제어기와 로봇 256대가 같은 계단을 같은 위치에서** 내려간다. 다리 목표 속도 제한도 모두 같다. 계단 3개의 평균 ± 표준편차로 적었다. PD는 별도 시드에서 게인 24조합을 탐색해 고른 값(P 5, D 0.6)이다.

![계단 전체 내리막 비교](assets/mujoco-descent-flight.png)
*왼쪽은 제어기 비교, 오른쪽은 입력을 빼고 재학습한 정책. 위부터 네 바퀴 중 최대 하중(50 ms 평균), 5 ms 순간 하중, 베이스 피치. 0초는 앞바퀴 아래 지면이 내려가기 시작한 순간이다.*

### 제어기 비교

| 조건 | 최대 피치 (°) | 피치 RMS (°) | 피치 속도 RMS (°/s) | 앞바퀴 하중 50 ms (N) | 뒷바퀴 하중 50 ms (N) | 앞바퀴 5 ms (N) |
|---|---|---|---|---|---|---|
| **강화학습 (exp10 실제 로봇용)** | 2.70 ± 0.83 | 1.12 ± 0.51 | 5.5 ± 1.2 | 1205 ± 91 | 1147 ± 75 | 4280 ± 252 |
| PD (튜닝) | 4.53 ± 0.13 | 1.73 ± 0.19 | 16.9 ± 2.0 | 1279 ± 74 | 1059 ± 109 | 4476 ± 253 |
| 비선형 P | 13.48 ± 2.55 | 7.04 ± 1.45 | 12.9 ± 2.6 | 1174 ± 78 | 1035 ± 56 | 4241 ± 170 |
| 수평 제어 없음 | 16.89 ± 5.47 | 10.64 ± 2.34 | 12.8 ± 2.5 | 1180 ± 65 | 976 ± 64 | 4260 ± 72 |

- **차체 흔들림:** 강화학습의 최대 피치는 튜닝 PD보다 약 40% 작고, 피치 속도 RMS는 약 3분의 1이다. PD는 차체가 기운 뒤 다리를 늘려 되돌리기 때문에 단마다 출렁인다.
- **바퀴 하중:** 모든 바퀴가 모든 단을 내려갈 때의 최대 하중을 한 번씩 세면, 제어기 사이에 **뚜렷한 차이가 없다.** 강화학습이 충격을 줄였다고 말할 수 없고, 늘렸다고 말할 수도 없다.
- **튜닝 PD의 안정성:** 256대 중 20–27대의 주행이 시험 시간 전에 끝났다. 다른 제어기는 0대였다. 종료 원인은 따로 분석하지 않았다.

### 왜 다리를 뻗어도 하중이 줄지 않나

직관적으로는 강화학습은 다리(구동부)만 부딪히고 PD는 차체 전체가 숙여지며 부딪히니 강화학습의 하중이 더 작아야 한다. 측정과 모델을 보면 그렇지 않은 이유가 세 가지 있다.

1. **구동부가 가볍지 않다.** 현재 모델에서 바퀴와 함께 움직이는 질량은 다리 하나당 27.8 kg이고, 바퀴 하나의 정적 분담은 35.2 kg이다. 베이스는 23 kg뿐이고 전체 140.9 kg의 83%가 네 다리에 있다.
2. **PD도 로봇 전체 무게로 부딪히지 않는다.** 뒷바퀴를 축으로 앞이 숙여질 때 앞바퀴 하나의 유효 질량은 계산상 약 33 kg이다.
3. **강화학습도 차체가 함께 내려간다.** 앞바퀴 착지 직전 속도는 강화학습 0.77 m/s(차체 0.54 + 다리 0.23), 튜닝 PD 0.56 m/s(차체 0.54 + 다리 0.02)이다.

접지 뒤 강화학습이 다리를 더 뻗지 못하게 해도 앞바퀴 하중은 줄지 않았다(1200 → 1280 N). 5 ms 순간 하중은 시뮬레이터의 접촉 강성에 크게 좌우되므로 실제 하중으로 인용하면 안 된다. 또 시뮬레이션의 다리 서보에는 **힘 제한이 없고**, 질량 분포도 실제 로봇과 대조하지 않았다. 그래서 하중은 **같은 시뮬레이션 안의 상대 비교**로만 해석한다.

### 어떤 입력이 중요한가

exp10에서 한 입력만 정책에서 빼고 2000번 더 학습했다. 비평가는 모든 정보를 그대로 본다. 기준은 입력을 그대로 두고 똑같이 더 학습한 exp16(입력 연구 대조군)이다.

| 조건 | 최대 피치 (°) | 피치 RMS (°) | 피치 속도 RMS (°/s) | 앞바퀴 하중 50 ms (N) | 뒷바퀴 하중 50 ms (N) | 앞바퀴 5 ms (N) |
|---|---|---|---|---|---|---|
| 대조군 (exp16) | 2.96 ± 0.77 | 1.51 ± 0.50 | 4.7 ± 0.5 | 1284 ± 45 | 1050 ± 64 | 4382 ± 135 |
| 다리 힘 뺌 (exp17) | 2.81 ± 0.55 | 1.22 ± 0.39 | 5.4 ± 1.1 | 1055 ± 23 | 994 ± 58 | 3897 ± 106 |
| 다리 힘·속도 뺌 (exp18) | 3.15 ± 0.26 | 1.43 ± 0.30 | 6.6 ± 1.0 | 1169 ± 62 | 830 ± 28 | 3934 ± 187 |
| 바퀴 속도 뺌 (exp19) | 4.28 ± 0.72 | 2.19 ± 0.64 | 5.8 ± 1.0 | 1167 ± 73 | 1159 ± 13 | 4103 ± 211 |
| 베이스 기울기 뺌 (exp11) | 16.52 ± 5.40 | 11.24 ± 2.83 | 8.9 ± 1.4 | 1314 ± 11 | 1024 ± 61 | 4224 ± 25 |

- **베이스 기울기가 결정적이다.** 이 입력을 빼면 최대 피치가 대조군의 5배 이상으로 커져 수평 제어가 없을 때와 비슷해진다. 다리 위치는 지면에 대한 차체 자세만 알려 주고 중력 방향은 알려 주지 않으며, 현재 정책은 과거 입력을 기억하지 않는다.
- **다리 힘은 필수가 아니다.** exp10에서 실행 중 다리 힘만 가리면 나빠지지만, 빼고 재학습하면 피치가 대조군과 비슷하다.
- **하중 차이는 잠정적이다.** exp17의 앞바퀴 하중과 exp18의 뒷바퀴 하중이 대조군보다 작게 나왔지만, 조건별 학습이 1회뿐이라 입력 때문이라고 확정할 수 없다.

!!! note "이 비교로 말할 수 있는 것"
    **말할 수 있다:** 같은 다리 속도 제한에서 강화학습은 계단 전체의 베이스 흔들림을 튜닝 PD보다 줄였고, 바퀴 하중을 뚜렷하게 늘리지 않았다. 현재 구조의 정책에서 수평 유지에는 베이스 기울기 입력이 결정적이었다.

    **아직 말할 수 없다:** 선제적 동작, 충격 감소, 실제 하중의 절대값, 비스듬한 진입에서의 성능, 입력 효과의 학습 시드 간 재현성(조건별 학습 1회).

## 정리: 강화학습이 한 일

| | 식 기반 제어로 충분한 것 | 강화학습이 더 잘한 것 |
|---|---|---|
| 바퀴 방향·속도 | 기하학 식으로 정확히 계산된다 | — |
| 평지·완만한 지형에서 수평 | PD가 같거나 조금 더 낫다 | — |
| 바퀴가 뜨는 상황 | PD는 접지 센서가 있어야 안전하다 (없으면 넘어짐) | 다리 힘·관절 움직임만으로 알아채고 대응, 넘어짐 0 |
| 거친 지형에서 속도 유지 | | 바퀴·조향 보정으로 속도 오차가 절반 이하 |
| 계단 넘기 | 수평을 너무 빨리 맞추면 오히려 방해 | 기울기를 조금 허용하며 다리·바퀴를 함께 써서 멈추지 않음 |
| 경사처럼 오래 이어지는 기울기 | IMU 기울기를 되먹임하면 됨 | 강화학습도 기울기 입력이 있어야 함 (빼면 경사에서 8° 기욺) |
| 고속 회전·급정지 자세 | 목표 자세를 식으로 정해 줄 수 있음 (exp13처럼) | 안정 여유에 점수를 주면 스스로 안쪽으로 기울기 시작 (2°). 아직 작고 일정하지 않음 |

정리하면, **식으로 풀리는 부분은 식으로 두고, 상황마다 판단이 필요한 부분(바퀴가 뜰 때의 대응, 계단 오르기, 거친 지형)을 학습에 맡기는 구조가 맞았다.** 특히 실제 로봇에서 잴 수 있는 정보만 쓸 때 차이가 커졌다.

## 문제 해결 기록

!!! issue "높이맵 계단에서 로봇이 튀어 오름"
    **문제** 바퀴 반지름보다 훨씬 높은 16 cm 계단을, 정책 없이도 79% 넘었다.

    **원인** 촘촘한 높이맵의 벽에 바퀴가 닿을 때 시뮬레이터 계산이 튀어서 로봇이 점프했다.

    **해결** 계단을 상자로 쌓았다. 시험에서 "네 바퀴 모두 힘이 0인 시간"을 계속 재서 같은 오류를 감시한다.

!!! issue "계단을 더 배웠는데 계단이 나빠짐"
    **문제** 계단 지형으로 더 학습한 정책이 들쭉날쭉한 계단에서 오히려 못했다. 지형을 보여 준 정책은 더 나빴다.

    **원인** 지형 생성기가 바퀴로 오를 수 없는 17 cm 넘는 단을 만들고 있었다.

    **해결** 계단 높이를 14.5 cm 이하로 제한하자, 다른 것은 그대로인데 99.9–100%가 되었다.

!!! issue "같은 정책인데 결과가 87% → 76%"
    **문제** 같은 정책을 다시 시험하자 계단 통과율이 크게 달랐다.

    **원인** 128번 시험으로는 운에 따라 ±3% 이상 흔들린다.

    **해결** 최종 비교는 1,024번씩 시험하고 오차 범위를 같이 표시했다. 오차 범위가 겹치면 차이가 있다고 말하지 않는다.

!!! issue "PC가 꺼지면서 학습도 멈춤"
    **문제** 학습 도중 세션이 끊기거나 PC가 꺼지면 학습이 사라졌다.

    **원인** 학습 프로그램이 작업 창에 묶여 있었다.

    **해결** 학습을 창과 분리해서 실행하고, 100회마다 저장한 지점에서 이어서 학습할 수 있게 했다. 진행 상황은 파일에 적어 둔다.

!!! issue "회전 방향을 바꿀 때 바퀴가 뜸"
    **문제** 회전 명령이 바뀌는 순간 네 바퀴 접지율이 떨어졌다.

    **원인** 조향이 ±90°까지만 돌아서, 반대 방향이 필요하면 바퀴를 거의 180° 돌려야 한다. 그동안 바퀴가 엉뚱한 방향으로 끌린다.

    **해결 (일부)** 조향이 덜 돌았을 때는 바퀴 속도를 줄였다. 접지율은 좋아졌지만 회전 반응이 느려졌다.

!!! lesson "배운 점"
    - 학습이 막히면 학습 방법보다 **로봇 모델과 제어 구조**부터 확인한다. 막혔던 원인 세 가지 중 두 가지가 물리 모델 문제였다.
    - 결과가 너무 좋으면 의심한다. 계단 통과율 100%가 시뮬레이터 오류 때문이었다.
    - "넘어지지 않음"과 "해냄"은 다르다. 시험은 목표를 직접 재야 한다.
    - **물리적으로 불가능한 상황을 학습에 넣으면 안 된다.** 정책이 포기하는 쪽으로 배운다.
    - 더 오래 학습한다고 좋아지지 않는다. 정책은 학습 곡선이 아니라 별도 시험으로 고른다.
    - 강화학습이 꼭 필요한지는 **잘 만든 기존 제어와 비교해야** 알 수 있다.

## 남은 일

- 급정지 명령도 학습에 섞어서, 뒷바퀴를 들지 않고 서는 법 배우기
- 실제 바퀴 모터 토크 사양을 넣고 계단 성능 다시 확인 (지금 60 N·m는 가정)
- 계단을 오를 때 네 바퀴 접지가 약 70%로 떨어짐. 모서리를 넘는 순간 바퀴 하중이 빠지는 것은 구르는 방식의 한계라 다리 동작으로 줄일 수 있는지 확인
- 고속 회전에서 더 크게 기울게 하려면: 위험 벌점을 더 키우거나, 더 빠른 속도(실제 모터 토크 사양 필요)에서 학습
- 학습한 정책을 ROS 조이스틱 시뮬과 실제 로봇에 연결
- 계단 내리막 입력 연구를 학습 시드 3개 이상으로 반복 (대조군, 다리 힘 제거, 베이스 기울기 제거)
- 실제 로봇의 질량 분포와 다리 구동기 힘 제한을 시뮬레이션에 반영한 뒤 바퀴 하중 다시 측정
- 착지 하중 벌점을 넣었을 때 피치와 하중의 상충 관계 확인

## 원리

??? 바퀴 방향과 속도를 계산하는 식 (스워브 역기구학)
    차체가 앞으로 `vx`, 옆으로 `vy`로 가면서 `wz`로 돌면, 차체 중심에서 `(x, y)`에 있는 바퀴는 `(vx − wz·y, vy + wz·x)`의 속도로 지나가야 한다. 바퀴를 이 방향으로 틀고 이 크기로 굴리면 미끄러지지 않는다. 조향은 ±90°까지만 돌기 때문에, 필요한 방향이 그 밖이면 반대 방향으로 틀고 바퀴를 거꾸로 돌린다.

??? 바퀴가 반지름보다 높은 단을 오르는 원리
    단 모서리가 바퀴 중심보다 조금 위에 닿으면, 모서리가 바퀴를 미는 힘은 바퀴를 뒤와 아래로 누른다. 그런데 바퀴가 굴러가며 모서리를 긁는 마찰력은 바퀴를 위로 끌어올린다. 마찰이 충분하면 바퀴가 모서리를 타고 오른다. 마찰계수가 1이면 이론상 바퀴 반지름의 약 1.7배(약 16 cm)까지 오를 수 있다. 다만 뒷바퀴가 차체를 앞으로 밀어 줘야 앞바퀴가 모서리에 눌리므로, 뒷바퀴 모터 힘도 충분해야 한다. 그래서 힘이 모자라면 뒷바퀴는 힘을 다 쓰고 앞바퀴는 헛도는 "멈춤"이 생긴다.

??? 쉬운 단계부터, 한 번에 하나씩 어렵게 하는 이유
    지형, 속도, 높이를 한꺼번에 어렵게 하면 성능이 떨어졌을 때 무엇 때문인지 알 수 없다. 한 단계에 하나씩만 바꾸면 원인을 찾기 쉽다. 쉬운 지형을 가끔 다시 보여 주는 것은, 어려운 지형만 보다가 평지 주행을 잊는 것을 막기 위해서다.

??? 정책에 새 입력을 추가하면서 기존 학습 결과 이어 쓰기
    exp08에서는 지형 높이 정보를 새 입력으로 추가했다. 새 입력에 연결된 가중치를 처음에 모두 0으로 두면, 새 입력이 무엇이든 처음에는 기존 정책과 똑같이 움직인다. 그 상태에서 학습을 이어 가면 처음부터 다시 배우지 않아도 된다.

## 부록: 이전 판의 상세 기록

읽기 쉽게 고치는 과정에서 본문에서 빠졌던 보상표, 넘어짐 판정, 지형 단계, 커리큘럼 등의 상세 내용을 복원했다. 당시 기록이므로 일부 수치와 설명은 위의 최신 내용과 다를 수 있다.

??? 이전 판 원문 (전방향 주행·지형 커리큘럼·계단 학습)

    **한 줄 요약**

    [MuJoCo 강화학습](11-mujoco-rl.md)의 명령을 **전진·횡이동·회전 속도와 지면 기준 높이** `(vx, vy, wz, h)`로 바꾸고, 스워브(4륜 독립 조향) 역기구학 위에 정책이 보정만 하는 구조로 다시 만들었다. 4바퀴 접촉이 안 되던 원인 세 가지를 찾아 고친 뒤 8단계 커리큘럼을 **약 700회 만에 끝까지** 올라갔다. 학습에 쓰지 않은 지형 28개 시나리오에서 **넘어짐 0**, 평균 속도 오차 0.056 m/s, 높이 오차 0.5 cm, 4바퀴 동시 접촉 96%. 남은 약점은 고난도 지형에서 랜덤 명령을 줄 때의 접촉(74~80%)과 회전 시 안쪽으로 덜 기우는 것.

    **이어서 (계단):** 높이맵으로 만든 계단은 경사로가 되거나 충돌 오류로 로봇이 튀어 올라서, 계단을 **박스 지오메트리로 다시 만들고** "넘어지지 않음"이 아니라 **실제로 계단을 통과했는지**를 재는 평가를 만들었다. 기존 정책(exp05)이 이미 6–9 cm 계단은 100%, 최대 14 cm급 오르막은 95% 통과했고, 계단 지형으로 추가 학습한 정책들은 지형 정보 유무와 상관없이 오히려 **불규칙한 높은 계단에서 나빠졌다**(0.95 → 0.89, 0.64). 원인 후보를 찾아 고치는 실험을 이어가는 중이다. 아래 계단 주행 부터.

    ![박스 계단을 오르는 Teraffe](assets/mujoco-stairs-hero.jpg)
    *레벨 6 박스 계단(단 높이 9.6–14.4 cm, 바퀴 반지름 9.6 cm) 오르막. 앞바퀴가 단 위로 올라선 순간.*

    **한 일**

    - 명령을 `(vx, vy, wz, 높이)`로 바꾸고 높이 기준을 **네 바퀴 아래 지면 평균 위의 차체 높이**로 정함
    - 스워브 역기구학 피드포워드 + 정책 잔차, 대각선 하중 균형기
    - 8종 지형(평지·경사·물결·요철·범프·계단·턱·혼합) 5레벨 뱅크 + 8단계 성과 기반 커리큘럼(쉬운 지형 복습 25%)
    - 넘어짐 판정 4가지(기울기·낮은 높이·지속 기울어짐·NaN)와 경계/시간 초과 구분
    - 회전 시 **안쪽으로 기우는 목표 자세**(구심 가속도 기반, 높이가 높을수록 크게)
    - 학습에 쓰지 않은 지형 시드로 28개 시나리오를 도는 평가기, 실험 6개(exp01~05)
    - 키보드로 **누르는 동안만** 움직이는 직접 조종 뷰어

    **명령**

    | 항목 | 범위 | 기준 |
    |---|---|---|
    | vx (전진) | −1.0 ~ 1.3 m/s | 차체 좌표 |
    | vy (횡이동) | ±0.8 m/s | 차체 좌표, + 왼쪽 |
    | wz (회전) | ±1.0 rad/s | + 반시계(좌회전) |
    | 높이 | 1.5 ~ 2.9 m | 차체 원점 − 네 바퀴 아래 지면 높이 평균 |

    명령은 3~6초마다 다시 뽑는다. 전진만, 횡이동만, 제자리 회전, 조합, 정지, 무작위 6가지 모드를 섞는다. 정책에는 목표값이 아니라 **기울기 제한을 건 명령**(가속 1.0 m/s², 회전 가속 1.5 rad/s², 높이 0.25 m/s)이 들어간다. 바퀴 림 속도(1.35 m/s)와 횡가속도(무게중심 높이·바퀴 간격 기준 전복 여유) 안에 들도록 속도를 줄여서 뽑는다.

    **제어 구조: 스워브 IK + 잔차**

    정책이 처음부터 바퀴 12개를 다 정하지 않는다. 명령에서 바퀴마다 필요한 속도를 계산해 주고, 정책은 그 위에 보정만 한다.

    | 그룹 | 피드포워드 | 정책 잔차 |
    |---|---|---|
    | 조향 4 | `v_i = (vx − wz·y_i, vy + wz·x_i)`의 방향, ±90° 안으로 접고 0.35 rad 히스테리시스 | ±0.3 rad |
    | 바퀴 4 | 위 속도를 **실제 조향 방향에 투영**한 값 / 반지름 | ±4 rad/s |
    | 다리 4 | 명령 높이에 맞는 기본 신장 + 지형 적응 + 하중 균형기 | **속도(증분) 행동**, 최대 0.5 m/s, 누적 ±0.5 m |

    - **하중 균형기:** 다리 4개가 모두 위치 제어라 정적 부정정이다. 대각선 다리 길이가 조금만 어긋나도 한 대각선이 들린다. `(F1+F4) − (F2+F3)`를 0으로 만드는 적분기(이득 0.3, ±0.35)가 대각 패턴 `[+1, −1, −1, +1]`로 다리를 보정한다.
    - **정렬 스케일링 (exp04):** 조향이 아직 목표 방향으로 돌지 않았을 때 바퀴를 돌리면 옆으로 끌린다. 가장 많이 어긋난 바퀴의 오차로 피드포워드를 `cos²(오차)`만큼 줄인다.

    **관측 (정책 63, 가치함수 87)**

    | 정책 관측 | 개수 |
    |---|---|
    | 차체 선속도·각속도, 중력 방향 | 9 |
    | 명령(기울기 제한 적용), 실제 높이 | 5 |
    | 다리 신장·조향 각도·다리 속도·조향 속도·바퀴 속도·다리 힘 | 24 |

    | IK 조향·바퀴 피드포워드, 하중 균형기 상태 | 9 |
    | 누적 다리 보정 | 4 |

    가치함수(비대칭 critic)는 여기에 바퀴 접촉·법선력, 바퀴 아래 지면 높이, 지지다각형 여유, 마찰·질량·강성 배율, 목표 자세, 바퀴별 공중 시간, 무게중심 높이·수직 속도를 더 본다. 정책은 **지형을 보지 않는다**(높이 스캔 없음).

    **계단 주행 (3차 개선)**

    **이 부분 요약**

    목표는 기존 전방향 주행·높이·자세 성능을 지키면서 **실제 수직 단차가 있는 계단을 오르내리는 것**이었다. (1) 높이맵 계단의 한계를 확인하고 계단을 박스로 다시 만들었고, (2) 계단 통과를 직접 재는 평가와 다중 시드 벤치마크를 만들었으며, (3) 기존 정책을 이어서 계단 지형으로 학습하는 실험을 세 가지(지형 정보 없음, 바퀴 주변 높이 스캔, 계단 높이 상한) 진행했다. **현재까지 계단 성능이 가장 좋은 정책은 계단 학습 전의 exp05**이고, 추가 학습은 불규칙한 높은 계단에서 정체를 늘렸다.

    | 항목 | 내용 |
    |---|---|
    | 유지한 것 | 스워브 IK + 잔차, 구 충돌 바퀴, 대각 하중 균형기, 다리 증분 행동, 성과 기반 커리큘럼 |
    | 새로 만든 것 | 박스 계단(환경마다 다른 위치·높이), 좌우 높이가 다른 지형, 바퀴 토크 제한, 계단 통과 평가 13종, 다중 시드 벤치마크, 정체 진단, 바퀴 주변 높이 스캔, 가중치 이어받기(warm start) |
    | 실험 | exp07 (지형 정보 없음), exp08 (높이 스캔), exp09 (계단 높이 상한, 진행 중) |

    **계단 지형: 높이맵의 한계와 박스 계단**

    MuJoCo 높이맵은 격자점 사이를 삼각형으로 잇는다. 그래서 계단의 수직면은 항상 **격자 한 칸 폭의 경사**가 된다. 앞에서 "어려운 지형"으로 만든 7.5 cm 격자에서 14 cm 단은 62° 경사로였고, 정책은 이것을 경사로처럼 올라갔다.

    | 격자 간격 | 12.5 cm 단의 실제 모양 | 문제 |
    |---|---|---|
    | 15 cm (기존) | 40° 경사 | 계단이 아니라 경사로 |
    | 7.5 cm | 59° 경사 | 여전히 경사로 |
    | 2.5 cm | 79° 경사 | 바퀴가 얇은 삼각기둥 옆면에 걸리면 **공중으로 튀어 오름** |

    격자를 2.5 cm로 줄이면 거의 수직이 되지만, 높은 단에서 바퀴가 2.5 cm 폭 삼각기둥들과 동시에 부딪히며 접촉 해가 튀었다. 정책 없이 IK만 돌려도 단에 닿는 순간 네 바퀴 힘이 모두 0이 되고 앞바퀴가 23–31 cm 떠오른 뒤 넘어졌다. 그 상태에서 잰 "계단 성공률 100%"는 이 오류 덕분이었다.

    ![높이맵 계단과 박스 계단에서 IK만으로 첫 단을 오를 때](assets/mujoco-stairs-artifact.png)
    *정책 잔차 0(IK만), 0.5 m/s. 왼쪽: 높이맵 계단에서는 단에 닿자 앞바퀴 힘이 0이 되고(공중) 떠오른 뒤 넘어짐. 오른쪽: 박스 계단에서는 힘을 유지한 채 모서리를 타고 올라감.*

    **해결:** 계단의 각 단을 **박스 지오메트리 기둥**으로 만들었다. MuJoCo Warp는 박스의 크기·경계 상자를 환경마다 따로 둘 수 있어서, 리셋 때 그 환경의 지형에 맞는 계단(위치·방향·단 높이)을 쓴다. 구–박스 접촉은 해석적이라 수직면이 정확하다. 높이맵에는 단을 넣지 않고(그 아래는 평지나 요철), 높이 기준·다리 지형 적응·평가용 높이 조회에만 박스 윗면을 합친다.

    **월드에 붙은 지오메트리는 위치가 갱신되지 않음**

    **문제** 박스 크기를 환경마다 바꿨는데 바퀴가 박스를 통과했다.

    **원인** MuJoCo Warp(그리고 CPU MuJoCo도)는 월드 바디에 붙은 지오메트리를 정적인 것으로 보고 위치·회전을 데이터를 만들 때 한 번만 계산한다. `geom_pos`를 바꿔도 반영되지 않는다.

    **해결** 리셋 때 박스의 월드 위치·회전 행렬(`geom_xpos`, `geom_xmat`)을 환경별 데이터에 직접 쓰고, 크기·경계 상자·경계 구 반지름은 환경별 모델 값으로 바꿨다. 렌더링용 CPU 데이터에도 같은 값을 써야 화면에 계단이 보인다.

    | 새 지형 | 내용 (레벨 4 → 레벨 6) |
    |---|---|
    | 박스 계단 | N단 오르막 → 층계참 2–3.5 m → N단 내리막. 단 높이 6–9 cm → 9.6–14.4 cm, 단 너비 0.35–0.8 m, 2–6단. 절반은 같은 높이, 절반은 ±35% 불규칙 |
    | 요철 + 계단 | 박스 계단 주변에 촘촘한 요철 |
    | 좌우 높이차 (split) | 회전된 평평한 판 여러 개(높이 2–6 cm × 배율). 좌우·앞뒤 바퀴가 다른 높이를 밟음 |
    | 기존 지형 | 경사·물결·요철·범프·턱·혼합. 높이맵 5 cm 격자, 요철 파장 0.67 m, 높이 한도 2.0 m |

    ![레벨 6 계단 오르막](assets/mujoco-stairs-up.jpg)
    *레벨 6 박스 계단 오르막 (exp08 정책). 앞바퀴가 단 위, 뒷바퀴는 아직 아래 지면.*

    **바퀴 토크 제한:** 기존 모델은 바퀴 구동 토크가 무제한이었다. 실제 모터 사양이 프로젝트에 없어서, 마찰로 낼 수 있는 토크(바퀴당 약 35 N·m = 마찰 1.0 × 하중 350 N × 반지름 0.096 m)를 넘는 여유를 두고 **바퀴당 60 N·m를 가정**했다. 계단 성능은 이 값에 따라 달라지므로 실물 사양을 받으면 다시 맞춰야 한다.

    **어디까지가 현실적인가:** 구동 바퀴가 단 모서리에 눌리면 모서리에서 바퀴를 위로 미는 마찰력이 생긴다. 접촉점이 바퀴 중심보다 각 θ만큼 위에 있으면 마찰계수가 tan θ보다 커야 오를 수 있고, 마찰 1.0이면 이론상 단 높이 ≈ 1.7 × 반지름(약 16 cm)까지다. 마찰을 0.7로 낮추면 약 15 cm다. 그래서 단 높이를 이 범위 안(레벨 6 기준 최대 14.4 cm)에 두고, 그보다 높은 계단은 학습시키지 않기로 했다.

    **계단 통과 평가**

    넘어지지 않고 20초를 버틴 것과 계단을 넘은 것은 다르다. 그래서 평가를 따로 만들었다.

    | 항목 | 정의 |
    |---|---|
    | 출발 | 오르막: 첫 단 1.2 m 앞, 계단을 바라보는 방향. 내리막: 꼭대기 층계참 |
    | 성공 | 마지막 단을 지나 **1.7 m(휠베이스 + 여유) 더** 전진. 넘어지거나 지형 밖으로 나가면 실패, 시간 안에 못 넘으면 정체 |
    | 정체 비율 | 넘기 전까지 진행 방향 속도가 명령의 25% 미만인 시간 비율 |
    | 기타 | 통과 시간, 4바퀴·바퀴별 접촉률, 최대 기울기, **네 바퀴 모두 힘 0인 비율(물리 오류 감시)** |
    | 시나리오 13종 | 오르막/내리막 × 레벨 4·최고 레벨, 같은 높이/불규칙, 요철+계단, 주행 중 높이 변화(1.6↔2.8 m), 0.9 m/s, 차체 높이 2.8 m |

    처음에는 시나리오마다 128번 시도했는데, 같은 정책을 다시 재도 성공률이 0.87 → 0.76으로 흔들렸다(시도마다 계단·마찰이 달라짐). 128회의 표준오차는 약 0.03이라 0.05 정도의 차이는 판단할 수 없다. 그래서 **시드 2개 × 512회 = 1024회**를 모아 95% 구간을 함께 내는 벤치마크를 따로 만들고, 정책 비교는 이것으로 했다.

    **학습 전 시험: 기존 정책은 계단을 오를 수 있나**

    계단을 학습하지 않은 exp05 정책과 IK만(정책 잔차 0)을 박스 계단에 올려 봤다.

    **계단 학습 실험**

    모두 exp05 체크포인트에서 이어서, 같은 지형 설정·커리큘럼·학습 시드로 학습했다. 커리큘럼은 기존 8단계에 레벨 5·6 두 단계를 더해 10단계이고, 세 실험 모두 수십 회 만에 마지막 단계에 올랐다.

    | 실험 | 바꾼 것 (exp05 대비) | 결과 |
    |---|---|---|
    | exp06 | 7.5 cm 격자 고난도 지형 | 세션 종료와 함께 프로세스가 죽음 (체크포인트 없음). 이후 학습은 세션과 분리해 실행 |
    | exp07 | 박스 계단 지형으로 추가 학습 (관측 그대로) | 1100회 동안 정체, 불규칙 오르막 0.946 → **0.886**. 7000회에서 중단 |

    **기존 성능은 지켜졌나**

    계단 지형 평가 묶음 안의 기존 시나리오(평지·회전·높이 변화·고난도 지형 등)에서는 세 정책 모두 넘어짐 0, 평균 4바퀴 접촉 0.904–0.908, 성공률 0.990–0.999였다. 평균 속도 오차는 exp05 0.057 → 0.067–0.068 m/s로 조금 늘었다. 기존 지형 뱅크로 잰 원래 28개 시나리오 비교는 최종 정책을 정한 뒤 다시 잰다.

    **트러블슈팅**

    **제자리 회전만 하면 바퀴 하중이 0과 700 N을 오감**

    **문제** 정책 없이 IK만으로 제자리 회전을 시켜도 4바퀴 접촉률이 0.81, 법선력이 0 ↔ 700 N으로 튀었다. 직진·횡이동은 정상.

    **원인** MuJoCo Warp는 높이맵–원기둥 쌍에 접촉점을 **하나만** 만든다. 조향하면 원기둥 모서리 쪽으로 그 한 점이 옮겨 다니며 채터링이 난다.

    **해결** 바퀴 충돌 형상을 같은 반지름의 구로 바꿨다. 0.81 → 0.999. 원기둥 경고도 사라졌다.

    **한 대각선 바퀴 두 개가 같이 뜸**

    **문제** 평지에서도 한 대각선 바퀴 쌍의 하중이 거의 0이 됐다.

    **원인** 강성 높은 위치 제어 다리 4개는 정적 부정정이다. 대각 다리 길이가 3 cm만 어긋나도 한 대각선이 들리고, 정책은 이것을 보정할 신호가 약하다.

    **해결** 대각 하중 차를 0으로 만드는 적분기를 다리 피드포워드에 넣었다. 같은 3 cm 편향에서 접촉 0.00 → 0.985. 이득을 0.6, 1.0으로 올리면 오히려 나빠져서 0.3을 유지했다.

    **다리가 20 Hz로 떨면서 바퀴가 뜸**

    **문제** 커리큘럼이 1단계에서 멈추고, 학습할수록 탐색 표준편차가 0.20 → 0.28로 커졌다. 결정적 정책의 다리 행동이 매 스텝 +1과 −1을 오갔다.

    **원인** 다리 행동이 절대 목표였고 변화율 제한(스텝당 2.5 cm)이 걸려 있었다. 목표가 멀면 **부호만 의미가 있으니** 정책이 부호 제어(bang-bang)를 배웠고, 다리가 ±2.4 cm로 떨며 하중이 빠졌다. 같은 명령에서 행동을 0으로 두면 접촉은 0.99~1.0이었다.

    **해결** 다리 행동을 **속도(증분)**로 바꾸고 다리 속도 크기에 벌점을 줬다. 엔트로피 계수도 0.005 → 0.002로 낮췄다. 그 결과 약 700회 만에 최종 단계에 도달했다.

    **승급 기준 접촉률 0.95에 영원히 못 닿음**

    **문제** 결정적 정책은 평지 접촉이 0.91~1.0인데, 학습 중 측정값은 0.93에서 멈췄다.

    **원인** 학습 중 지표는 탐색 잡음이 섞인 확률적 정책으로 잰 값이다.

    **해결** 레벨별 기준을 0.90 → 0.75로 낮추고, 진짜 성능은 별도의 결정적 평가로 쟀다.

    **조향 반전 때 접촉이 0.43까지 떨어짐**

    **문제** 회전 명령이 클수록, 명령이 바뀌는 순간마다 접촉이 떨어졌다(|wz| ≥ 0.7에서 0.71).

    **원인** 조향을 ±90°로 제한하니 반대 방향이 필요할 때 180° 넘겨 뒤집어야 하고, 그동안 바퀴가 엉뚱한 방향으로 굴러 끌렸다. 조향 오차가 0.5 rad를 넘는 구간은 행동 0에서도 접촉 0.43.

    **해결(부분)** 정렬 스케일링으로 고난도 지형 접촉을 0.74 → 0.80으로 올렸다. 대신 회전 응답이 느려져 회전 오차가 0.057 → 0.080 rad/s로 늘었고, 리워드 강화(exp05)로는 되돌리지 못했다.

    **높이맵 계단에서 로봇이 튀어 오름**

    **문제** 2.5 cm 격자 높이맵 계단에서 IK만으로도 16 cm 계단 성공률이 79%였다. 바퀴 반지름(9.6 cm)보다 훨씬 높은 단이다.

    **원인** 바퀴 구가 얇은 삼각기둥 여러 개의 옆면과 동시에 부딪히며 접촉 해가 튀었다. 단에 닿는 순간 네 바퀴 힘이 모두 0이 되고 차체가 떠올랐다. 성공은 이 오류로 "점프"한 결과였다.

    **해결** 계단을 박스 지오메트리로 바꿨다. 평가에 "네 바퀴 모두 힘 0인 비율"을 넣어 같은 오류를 계속 감시한다(박스 계단 0.4–2%, 대부분 리셋 직후 낙하).

    **세션이 끝나자 학습도 같이 죽음**

    **문제** exp06이 5562회(이어서 학습 61회째)에서 체크포인트도 없이 사라졌다.

    **원인** 학습을 에이전트 셸에서 `nohup`으로만 띄워, 셸 세션이 끝날 때 같은 프로세스 그룹으로 정리됐다.

    **해결** 학습은 `setsid nohup`으로 세션과 완전히 분리하고, 진행 상황·재개 방법을 상태 파일에 적어 새 세션에서 중복 없이 이어 갈 수 있게 했다.

    **같은 정책인데 계단 성공률이 0.87 → 0.76**

    **문제** 같은 체크포인트를 다시 평가하자 불규칙 계단 성공률이 크게 달랐다.

    **원인** 128회 단일 시도는 표준오차가 약 0.03이고, 시도마다 뽑히는 계단·마찰이 달라 흔들림이 더 컸다.

    **해결** 시드 2개 × 512회 벤치마크와 95% 구간으로 비교한다. 128회 결과로 낸 "0.95 vs 0.84" 같은 판단은 다시 확인했다.

    **계단을 더 학습시켰는데 계단이 나빠짐**

    **문제** exp07·exp08 모두 불규칙한 높은 계단 오르막에서 exp05보다 나빠졌다. 지형 정보를 준 exp08이 더 나빴다.

    **원인 (조사 중)** 정체한 시도는 뒷바퀴 토크 포화 + 앞바퀴 헛돌기였고, 마찰·토크 가정만으로는 설명되지 않았다. 지형 생성기가 이론적인 등판 한계(약 15–16 cm)를 넘는 불규칙 단(최대 17.4 cm)을 만들고 있었다.

    **해결 (진행 중)** 모든 단을 14.5 cm 이하로 자르는 것만 바꾼 exp09로 확인 중. 나빠진 정책은 채택하지 않고, 지금 최종 후보는 exp05다.

    **배운 점**

    - 접촉이 안 될 때 리워드부터 만지지 말고, **행동 0(IK만)일 때**의 접촉을 먼저 쟀다. 세 원인 중 둘(충돌 형상, 대각 하중)은 정책과 상관없는 물리 문제였다.
    - 절대 목표 + 변화율 제한 조합은 정책이 부호만 쓰는 bang-bang을 배우기 쉽다. 증분 행동이 더 안전하다.
    - 학습 중 지표와 결정적 평가는 다르다. 승급 기준은 학습 중 지표 기준으로 정해야 한다.
    - 개선은 시드 세 개에서 방향이 같을 때만 채택했다. exp05처럼 효과가 없으면 그대로 기록한다.
    - "어렵게 만들었다"고 생각한 지형이 해상도와 높이 한도 때문에 실제로는 쉬웠다. 지형은 숫자가 아니라 **실제 높이맵**으로 확인해야 한다.
    - 계단 성공률 100%가 물리 오류 때문일 수 있다. 숫자가 좋으면 오히려 바퀴 힘과 영상을 확인해야 했다.
    - "넘어지지 않음"과 "통과함"은 다르다. 평가 지표가 목표를 직접 재야 한다.
    - 작은 표본의 차이는 판단 근거가 아니다. 정책 비교는 신뢰구간이 겹치지 않을 때만 한다.
    - 더 학습시킨 정책이 더 나쁠 수 있다. 학습 곡선이 아니라 별도 평가로 고른다.

    **남은 점**

    - 회전 시 안쪽 기울기가 −0.2 ~ −1.3°로, 목표 −2 ~ −3°의 1/3 이하
    - 정렬 스케일링의 회전 추종 손실 (조향 반전 자체를 줄이는 방법이 필요)
    - 계단 추가 학습이 불규칙한 높은 계단에서 성능을 떨어뜨리는 원인 확정 (exp09: 단 높이 상한)
    - 높이 스캔은 이번 설정에서 효과가 없었음. 보상(정체 시 계속 밀도록)·커리큘럼과 함께 다시 시험
    - 실제 바퀴 모터 토크 사양 반영 (지금 60 N·m는 가정)
    - 계단 위 4바퀴 접촉률 0.6–0.8: 단 모서리를 오를 때 바퀴 하중이 순간적으로 빠지는 것은 구르는 방식의 한계
    - 높이 2.9 m에서 전진 1.3 m/s + 회전 1.0 rad/s 같은 불가능 명령은 넘어지지는 않지만 접촉 0.32~0.37. 실제 운용에서는 명령 제한이 걸러야 함
    - 학습한 정책을 ROS 조이스틱 시뮬이나 실물과 연결

    **원리**

    **IK와 ±90° 조향**

    차체가 `(vx, vy)`로 가면서 `wz`로 돌면, 차체 위 점 `(x_i, y_i)`의 속도는 `(vx − wz·y_i, vy + wz·x_i)`다. 바퀴는 이 방향으로 조향하고 이 크기로 구르면 미끄러지지 않는다. 조향을 ±90°로 제한하면 `δ`와 `δ ± π` 중 가까운 쪽을 고르고 바퀴를 거꾸로 돌린다. 경계 근처에서 두 해를 오가지 않도록 0.35 rad 히스테리시스를 둔다. 바퀴 속도는 목표 방향이 아니라 **지금 실제 조향 방향**으로 투영해서, 조향이 덜 돌았을 때 옆으로 끌리는 성분을 줄인다.

    **시 안쪽으로 기울이기**

    회전하면 구심 가속도 `a = (−wz·vy, wz·vx)`가 생기고, 차체가 수평이면 그만큼 바깥쪽 바퀴로 하중이 몰린다. 목표 roll을 `−λ·atan(a_y / g)`, pitch를 `λ·atan(a_x / g)`로 두면 차체가 안쪽으로 기울어 합력이 지지다각형 가운데로 온다. λ는 높이 1.5 m에서 0.3, 2.9 m에서 0.8이고 최대 6°로 자른다. 무게중심이 높을수록 같은 가속도에서 전복 모멘트가 커지기 때문이다. 좌회전(+wz)하며 전진하면 a_y > 0이고 목표 roll은 음수(왼쪽, 안쪽으로 기울어짐)다.

    **기반 커리큘럼에서 한 번에 한 축만 올리는 이유**

    지형, 속도, 높이 범위를 한꺼번에 올리면 성능이 떨어졌을 때 무엇 때문인지 알 수 없고, 정책이 동시에 여러 가지를 새로 배워야 한다. 단계마다 한 축만 바꾸면 강등이 일어났을 때 원인이 그 축으로 좁혀진다. 낮은 레벨을 25% 섞는 복습은 어려운 지형만 보다가 평지 성능을 잊는 것을 막는다.

    **반지름보다 높은 단을 오르는 원리**

    단 모서리가 바퀴 중심보다 각 θ만큼 위에 닿으면, 법선력은 바퀴를 뒤아래로 밀고(−cos θ, −sin θ), 바퀴를 굴리는 방향의 마찰력은 앞바퀴 접점에서 위쪽 성분(cos θ)을 가진다. 위로 오르려면 마찰력 × cos θ > 법선력 × sin θ, 즉 **마찰계수 > tan θ**가 필요하다. 법선력은 뒷바퀴가 차체를 밀어 주는 힘에서 나오므로 뒷바퀴의 견인력(토크·마찰)도 함께 필요하다. 마찰 1.0이면 θ < 45°, 단 높이 < r(1 + sin 45°) ≈ 1.7r. 그래서 토크가 모자라거나 단이 이 한계에 가까우면 뒷바퀴는 한계 토크로 밀고 앞바퀴는 헛도는 정체가 나타난다.

    **늘리면서 기존 가중치 이어받기 (warm start)**

    새 관측을 정책 입력 끝에 붙이고, 첫 층 가중치에서 새 입력에 해당하는 열을 0으로 채운다. 그러면 새 입력이 무엇이든 처음 출력은 이전 정책과 같다. 관측 정규화 통계도 새 입력 부분만 평균 0, 표준편차 0.1로 넣는다. 가치함수는 입력이 [정책 관측 | 추가 관측 | 가치함수 전용 관측] 순서라 새 열을 가운데에 끼운다. 옵티마이저 상태는 크기가 달라 새로 시작한다.

        ### 제어 구조: 계산은 식으로, 보정은 학습으로
        Teraffe는 바퀴 네 개가 각각 방향을 틀고(조향) 굴러가는(구동) 로봇이다. 차체를 어떻게 움직이고 싶은지 정하면, 바퀴마다 어느 방향으로 얼마나 빨리 굴러야 하는지는 **기하학 식으로 정확히 계산**된다. 이 계산을 역기구학(IK)이라고 한다.
        그래서 학습된 제어기(정책)가 바퀴 12개 관절을 처음부터 다 정하게 하지 않았다. 식으로 계산한 값을 기본으로 두고, 정책은 **그 위에 작은 보정만** 더한다.
        | 관절 | 기본값 (식으로 계산) | 정책이 더하는 보정 |
        | 조향 4개 | 바퀴가 가야 할 방향 | ±17° |
        | 바퀴 4개 | 바퀴가 굴러야 할 속도 | ±4 rad/s (약 ±0.4 m/s) |
        | 다리 4개 | 명령 높이에 맞는 다리 길이 | 다리마다 늘이고 줄이는 양 (최대 ±0.5 m) |
        정책이 아무것도 안 해도 평지에서는 명령대로 굴러간다. 정책은 **지형 때문에 생기는 차이**를 맞추는 역할을 맡는다. 예를 들어 바퀴마다 다른 높이의 땅을 밟을 때 다리를 따로 조절하거나, 미끄러짐을 보정한다.
        정책이 보는 정보는 차체의 속도·기울기, 관절 상태, 명령이다. **지형을 직접 보지는 않는다.** 바퀴가 무엇을 밟았는지는 다리에 걸리는 힘과 차체의 흔들림으로 느낀다.
