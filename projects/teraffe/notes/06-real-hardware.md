!!! summary "한 줄 요약"
    실물 Teraffe의 다리 리프트 하나는 주 모터 AK80-64, 보조 모터 Dynamixel XH430, 절대 엔코더 AMT212로 이뤄진다. 세 장치를 각각 CAN과 RS-485로 직접 통신하는 드라이버를 만들고, 네 다리의 상태를 한 화면에서 보고 조작하는 웹 UI까지 만들었다.

## 한 일

- 다리 한 개 = 주 모터 + 보조 모터 + 엔코더, 네 다리(FL, FR, RL, RR) 구성
- AK80-64 CAN 드라이버: 확장 프레임으로 ERPM·전류 명령
- Dynamixel 드라이버: Protocol 2.0, 전류 제어 모드
- AMT212 엔코더 읽기: 요청 1바이트 → 응답 2바이트, 체크섬 검사
- 네 다리 통합 웹 UI, 다리를 눌러 늘이고 줄이는 Tension 웹 UI, 장치별 데스크톱 모니터

## 리프트 메커니즘

![동작 메커니즘](assets/teraffe-mechanism.png)
*왼쪽부터: 다리를 편 전체 구조, 블록 체인 하우징, 3단 텔레스코픽 다리 링크, 조향·구동 일체형 바퀴 모듈.*

- **블록 체인 신축:** 블록을 여러 개 이은 체인을 모터로 밀어 다리를 직선으로 늘인다. 체인 끝은 다리 끝 링크에 연결돼 있고, 최대 3 m까지 늘어난다.
- **바퀴 모듈:** 조향 모터와 구동 모터를 한 모듈에 넣고, 서스펜션으로 바닥 충격을 흡수해 안정성을 높였다.

![다리 프로토타입](assets/teraffe-prototype.jpg)
*왼쪽부터: 신축 다리 프로토타입, 하우징 안의 블록 체인, 하우징 뒷면의 모터와 엔코더.*

CubeMars 모터가 블록 체인을 밀어 다리를 늘이고, Dynamixel이 체인 이송을 보조하며, 엔코더로 다리 각도를 잰다.

| 부품 | 역할 |
|---|---|
| CubeMars AK80-64 | 블록 체인을 미는 주 모터 |
| Dynamixel | 블록 체인 보조 |
| AMT212 엔코더 | 다리 각도 측정, 리밋 판단 |
| 하우징 | 블록 체인을 감아 두고 내보내는 통 |

아래 통신과 제어는 이 프로토타입의 모터와 엔코더를 대상으로 했다.

## 장치 구성

| 장치 | 역할 | 통신 | 명령 / 읽기 |
|---|---|---|---|
| AK80-64 (CubeMars) | 리프트 주 동력 | SocketCAN, 1 Mbps | ERPM (속도), 전류 |
| Dynamixel XH430 | 리프트 보조 동력 | RS-485, Protocol 2.0, 115200 | 전류 (A) |
| AMT212 | 다리 각도 측정 (절대값) | RS-485, 115200 | 14비트 각도 |

```text
Ubuntu PC
├── SocketCAN 어댑터 ── can0 ── AK80-64 × 4
└── RS-485 어댑터 ── /dev/ttyUSB0 ── Dynamixel × 4 + AMT212 × 4
```

네 다리(FL, FR, RL, RR)마다 AK80-64, Dynamixel, AMT212가 하나씩 붙는다. Dynamixel 4개와 엔코더 4개는 RS-485 버스 하나를 같이 쓰고, AK80-64 4개는 CAN 버스 하나를 같이 쓴다. 같은 버스 위의 장치는 ID로만 구분되므로, ID만 보고 "어느 다리의 어느 장치인지" 알 수 있게 규칙을 정했다.

| 다리 | AK80-64 (CAN ID) | Dynamixel (ID) | AMT212 (요청 바이트) |
|---|---|---|---|
| FL (앞 왼쪽) | 101 | 111 | `0x1C` |
| FR (앞 오른쪽) | 102 | 112 | `0x2C` |
| RL (뒤 왼쪽) | 103 | 113 | `0x3C` |
| RR (뒤 오른쪽) | 104 | 114 | `0x4C` |

- **끝자리 = 다리 번호**(1 FL, 2 FR, 3 RL, 4 RR). 세 장치 모두 같은 번호 순서를 따른다.
- **AK80-64는 10x, Dynamixel은 11x**로 장치 종류를 나눴다. 로그에 ID만 찍혀도 어떤 모터인지 바로 보인다.
- **엔코더 요청 바이트는 위 4비트에 다리 번호**, 아래 4비트는 `C`로 고정했다(`0x1C` ~ `0x4C`).

## AK80-64: CAN으로 속도 명령

- **확장 ID:** `모터 ID | (명령 번호 << 8)`. 예: ID 101에 속도 명령(3)이면 `0x365`.
- **데이터:** 32비트 정수, 빅엔디언 4바이트. 속도는 ERPM 그대로, 전류는 A × 1000.
- **범위 제한:** ERPM ±100,000, 전류 ±60 A로 코드에서 자른다.
- **단위:** ERPM은 전기적 회전수다. 극쌍 21, 감속비 64라서 `출력축 RPM = ERPM / 21 / 64`. 리프트 기본 500 ERPM은 출력축 약 0.37 rpm, Tension UI의 5000 ERPM은 약 3.7 rpm이다.
- **정지:** 0 ERPM.

## Dynamixel: 전류 모드로 보조

1. 토크 끄기 → 작동 모드를 전류 제어로 → 토크 켜기 (모드는 토크가 꺼져 있을 때만 바뀐다)
2. 목표 전류 쓰기. raw 1 = 2.69 mA로 환산
3. 정지는 0 A, 완전히 풀 때는 토크 끄기

보조 모터는 속도나 위치가 아니라 **일정한 힘(전류)**으로 주 모터를 돕는다. 늘릴 때 0.05 A, 줄일 때 0.2 A가 기본이다.

## AMT212: RS-485로 각도 읽기

1. 송신 모드로 바꾸고(RTS = False) 요청 바이트 1개를 보낸다.
2. 다 보내면(flush) 수신 모드로 바꾼다(RTS = True).
3. 10 ms 동안 최대 8바이트를 읽고, **마지막 2바이트**를 리틀엔디언 16비트로 읽는다.
4. 위 2비트는 체크 비트, 아래 14비트가 위치. 체크섬이 맞으면 `각도 = 위치 × 360 / 16383`.
5. 실패하면 10 ms 쉬고 최대 5번 다시 한다.

## 모니터링·조작 UI

| UI | 하는 일 |
|---|---|
| 통합 웹 UI | 네 다리의 AK·DXL·엔코더 상태를 브라우저에서 보고, AK ERPM과 DXL 전류를 직접 보냄 |
| Tension 웹 UI | 로봇 그림에서 다리를 눌러 늘이기·줄이기·정지 |
| 장치별 데스크톱 모니터 | AK, DXL, 엔코더 상태를 PyQt5 창으로 표시 |
| 주행·조향 모니터 | 외부 주행·조향 드라이버의 상태와 알람 표시 |

웹 UI는 장치마다 작업 스레드를 따로 두고, 2초 넘게 응답이 없는 장치는 미연결로 표시한다. 서버를 끄거나 연결을 다시 설정할 때는 명령을 보냈던 AK에 0 ERPM, DXL에 0 A를 먼저 보낸다.

## 트러블슈팅

!!! issue "엔코더가 응답하지 않음"
    **문제** AMT212에 요청을 보내도 응답이 없거나 길이가 맞지 않는 바이트가 왔다.

    **원인** RS-485는 한 선으로 보내고 받는 반이중 방식이라, 어댑터의 송수신 방향을 RTS 핀으로 직접 바꿔야 했다. 방향이 반대거나 바꾸는 시점이 어긋나면 응답을 놓치거나, 전환 순간의 잡음 바이트가 섞였다.

    **해결** RTS 극성과 전환 시점을 맞춰 송신 False → flush → 수신 True 순서로 정했다. 전환 순간의 잡음 바이트를 흡수하려고 8바이트까지 읽어 마지막 2바이트만 쓰고, 체크섬으로 검증한다.

!!! issue "USB 어댑터 번호가 바뀌어 장치가 뒤섞임"
    **문제** USB 어댑터를 다시 꽂거나 재부팅하면 `ttyUSB0`, `ttyUSB1` 번호가 바뀌어, Dynamixel 버스와 엔코더 버스가 서로 뒤바뀐 채 열렸다.

    **원인** 리눅스는 USB 시리얼 장치에 연결된 순서대로 번호를 붙인다.

    **해결** 포트마다 Dynamixel 응답과 엔코더 응답을 확인해 어떤 장치가 붙었는지 가려냈고, 실행할 때는 순서와 관계없이 고정되는 `/dev/serial/by-id/` 경로로 포트를 지정했다.

!!! lesson "배운 점"
    - RS-485 반이중 통신은 "언제 듣는 쪽으로 바꾸느냐"가 핵심이다. 어댑터가 자동으로 해 주는지부터 확인한다.
    - 새 장치는 명령을 보내기 전에 상태 읽기부터 확인한다. 잘못된 ID로 모터를 돌리는 사고를 막는다.
    - 모터 단위(ERPM, raw 전류)는 코드 한곳에서 실제 단위로 바꿔 두면 UI와 제어 코드가 같은 숫자를 본다.

## 남은 점

- 늘릴 때 보조 모터 전류 부호를 Tension UI(DXL **−0.05 A**)와 ROS 리프트 제어(DXL **+0.05 A**)에서 하나로 통일하기
- 웹 UI 제어 API에 인증이 없다. 내부망에서만 쓴다.

## 원리

??? CAN 확장 프레임과 VESC식 명령
    CAN은 여러 장치가 두 선(CAN_H, CAN_L)을 같이 쓰고, 메시지마다 ID를 붙여 누가 받을지 정한다. 확장 프레임은 ID가 29비트라 여기에 "어느 모터"와 "무슨 명령"을 같이 넣을 수 있다.

    AK 시리즈의 서보 모드는 VESC 방식이다. ID 아래 8비트가 모터 번호, 그 위가 명령 번호(0 듀티, 1 전류, 3 속도, 4 위치 …)다. 데이터 8바이트 중 앞 4바이트에 값을 빅엔디언으로 넣는다.

??? AMT212 체크 비트
    16비트 응답 중 아래 14비트가 위치다. 위 2비트 K1, K0는 홀짝 검사 비트다.

    - K1 = 위치의 **홀수 번째 비트**(1, 3, 5, …)를 XOR한 값의 반대
    - K0 = 위치의 **짝수 번째 비트**(0, 2, 4, …)를 XOR한 값의 반대

    받은 K1, K0가 직접 계산한 값과 다르면 통신 중 비트가 깨진 것이니 버리고 다시 읽는다.

??? RS-485 반이중과 RTS
    RS-485는 두 선의 전압 차이로 신호를 보내 잡음에 강하고 멀리 간다. 대신 같은 두 선으로 보내기와 받기를 번갈아 해야 한다(반이중). USB–RS485 어댑터 중 일부는 이 방향을 자동으로 바꾸고, 일부는 RTS 핀으로 직접 바꿔야 한다.

    보낸 뒤 너무 일찍 수신으로 바꾸면 아직 나가지 않은 바이트가 잘리고, 너무 늦게 바꾸면 장치의 응답 앞부분을 놓친다. 그래서 `flush()`로 송신 완료를 기다린 다음 바꾼다.
